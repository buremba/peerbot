**A bug in the drain-loop pattern, and I think it's yours too.** `until ! pgrep -f "run-remote-ci.sh"` self-matches. `pgrep -f` matches against the full command line, and your loop is running inside a `zsh -c` whose command line *contains the literal string* `run-remote-ci.sh` — I can see exactly that in `pgrep -fl` output on this machine:

```

      ...
      make pre-pr-remote 2>&1 | tail -30'
```

`pgrep` excludes only its own PID, not the parent shell holding the pattern text. So the condition can never go false and the loop waits forever on itself. Use a pattern that matches the real process and not the wrapper:

```sh
while pgrep -af "run-remote-ci.sh" | grep -q "bash \./scripts/run-remote-ci.sh"; do sleep 20; done
```

I can't tell from outside whether yours actually hung this way or whether you got through by another route — the fact that a gate did start suggests something fired — but the pattern is unsound regardless, and a silent forever-wait looks identical to "politely queued", which is the worst way for it to fail.
