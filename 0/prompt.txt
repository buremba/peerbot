### 1. SHOULD FIX BEFORE MERGE — warm-path grant reconcile revokes the nix-cache domains that connector packages required

The create path and the warm path disagree about `expectedDomains` when an agent's *only* nix packages are connector-contributed:

- Cold create: `deployment-manager.ts:1638-1650` folds `gh` into `validated.nixConfig.packages`, so `syncNetworkConfigGrants` (`deployment-manager.ts:1207-1214`) adds `NIX_CACHE_DOMAINS` (cache.nixos.org etc.) to the expected set and grants them (I confirmed the grants land in the test run output).
- Warm path: `message-consumer.ts:565-591` folds only **domains** into the payload, never packages. On the next message for a live deployment, `syncNetworkConfigGrants(dataWithTrace)` (`message-consumer.ts:1132`) sees `nixConfig` empty → nix-cache domains are not in `expectedDomains` → the unconditional PG reconcile (`deployment-manager.ts:1225-1237`) **revokes** them (they are not in the `NPM_REGISTRY_DOMAINS` exemption).

Failure scenario: org has a GitHub connection, agent has no own nix packages. First-ever deploy starts nix downloading `gh` (can take minutes); user sends a follow-up message 30s in; the warm-path sync revokes cache.nixos.org mid-download; if that traffic transits the proxy the worker boot wedges/fails in a way the agent can't explain. Even outside the race, grant rows flap revoke/re-grant on every warm→cold cycle, which defeats the stated "create and update can never diverge" single-sourcing (comment at `deployment-manager.ts:1671-1673`). Connector *egress* domains (api.github.com/github.com) do survive the warm path — but only because the consumer folds them; the packages half of the contribution was not given the same treatment. Natural fix: fold contributed packages (or at least the nix-cache condition) in the consumer alongside the domains.

### Follow-ups (not blockers)

1. **IP-literal egress grants**: `isValidDomainPattern` accepts `169.254.169.254` or `metadata.google.internal` (both match the 2-label regex). A hostile org-installed custom connector can silently widen *every* agent's egress to cloud-metadata endpoints — same power an operator has per-agent via settings, but org-wide and with no UI surfacing at install time. Consider rejecting IP literals/link-local here, and surfacing contributed domains at connector install.
