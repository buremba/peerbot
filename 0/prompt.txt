## 2. Fetch strategy: `users.list` bulk, not `users.info` per-user

`slack-web.ts` has **no** `usersList`. The existing `usersInfo` (line 195-206) is per-user and extracts only `is_admin`/`is_owner` — it is the wrong shape and would need extending anyway.

Rate-limit tiers:

| Method | Tier | Practical rate | Pagination |
|---|---|---|---|
| `users.list` | Tier 2 | ~20 req/min | cursor, `limit` up to 1000 (Slack recommends ≤200) |
| `users.info` | Tier 4 | ~100 req/min | n/a |
| `conversations.members` | Tier 4 | ~100 req/min | cursor (already implemented) |

For a 500-member workspace: `users.list` = 3 calls (well inside Tier 2), `users.info` = 500 calls ≈ 5 minutes of wall clock and burns the Tier-4 budget the ACL sync already spends on `conversations.members`. **`users.list` wins decisively**, and critically it is **once per team**, not per channel — the sync already loops `for (const [teamId, channelIds] of byTeam)` (`packages/server/src/authz/slack-acl-sync.ts:173`), which is the natural place to hoist one profile fetch.

Pagination helper to copy: `conversationMembers` at `slack-web.ts:158-179` — the exact `do/while` + `response_metadata.next_cursor` loop. `slackPost` already form-encodes correctly for `users.list`.

`users.list` also gives you `profile.real_name` / `profile.display_name` (fixes the title defect) and `deleted` / `is_bot` flags (lets you drop deactivated users and *all* bots, superseding the single-bot-id filter at `slack-acl-sync.ts:218-220`).

### The precedence trap — read this before writing code

There are **two different matchers** and they disagree, which decides whether email collapses or forks:

**Matcher 1 — `resolveMembers`** (`packages/server/src/authz/access-graph.ts:172-184`). Runs FIRST, for every member:
```ts
for (const id of m.identities) {
  const found = existing.get(`${id.namespace}|${id.value}`);
  if (found !== undefined) { hit = found; break; }   // ← first hit wins, array order
}
```
Equal-weight, **ignores `primary` entirely**, breaks on the first hit in **`m.identities` array order**, and has **no ambiguity detection**.

**Matcher 2 — `entity-link-upsert`** (`packages/server/src/utils/entity-link-upsert.ts:756-780`). Only sees members that MISSED matcher 1. Here `primary` *is* authoritative: because `slack_user_id` is primary and always present, **email is never consulted for matching** — `primaries.length &gt; 0` short-circuits the equal-weight union. Email would only ever be *accreted*, never *matched on*.

**Consequence:** all the collapse behavior you want lives in matcher 1, and it is decided by **the order you push identities into the array**. Push `email` **first**:

- New member, person already exists from Gmail/CRM → email hits → collapses onto the real person. ✅ This is the whole point of the work.
- **Already-created hollow entity** (the July-8 rows): `existing` will contain *both* `email|x@y → realPerson` and `slack_user_id|T:U → hollowEntity`. If `slack_user_id` is first, the hollow entity wins **forever** and the duplicate is permanent. If `email` is first, the member re-points to the real person and the hollow entity is orphaned.

So identity array order is load-bearing and deserves a comment at the call site. Also flag: matcher 1 silently picks a winner where matcher 2 would log `'entityLink merge candidate — multiple entities matched at the same identity tier'` (line 782-796). That divergence is a genuine latent bug, not introduced by this work, but this change is what makes it reachable.

**Identity accretion on an existing match does work** — `entity-link-upsert.ts:802-820` explicitly accretes non-`matchOnly` identities onto a matched entity. But that path only runs for members that *missed* matcher 1. A member that hits in matcher 1 returns straight from `resolveMembers` at line 181 and **never touches entity-link-upsert at all** — so it gains no email identity. That is a real gap: `resolveMembers` needs its own `insertIdentities`-equivalent for matched members, or the hit path must be routed through the upsert.

## 4. Backfill

**The good news: you probably don't need a migration.** A SQL migration *cannot* do this anyway — the email isn't in the database, it only exists behind a Slack API call. The sync is already a 15-minute cron that re-visits every member, so the fix is to make the sync self-healing:

**Title self-heal:** the exact precedent is already in the same file. `packages/server/src/authz/access-graph.ts:332-350` refreshes each **resource** entity's name after resolution, with this comment: *"`titlePath` only sets the name on auto-CREATE, so a name that wasn't available at first graph (or a later channel/repo RENAME) would otherwise stick to the stale value / the raw id."* It is idempotent via a `AND name &lt;&gt; ${name}` guard. **There is no equivalent loop for members** — add one. That is a ~15-line mirror of code that already exists 100 lines above.

**Identity self-heal:** covered by `entity-link-upsert.ts:802-809` accretion, *except* for the matcher-1-hit gap noted in §3.

**If you do need an out-of-band script**, the pattern is a `scripts/backfill-*.ts` one-off, not a migration. Concrete precedent: **`/Users/burakemre/Code/lobu/scripts/backfill-member-claims.ts`** — a one-time backfill of missing `$member` + `auth:signup` claims, with a guard test at `scripts/__tests__/backfill-member-claims-guard.test.ts`. Its header states the rule explicitly:

&gt; *"It is NOT a migration (docs/MIGRATIONS.md: no scan inside the blocking Helm hook)."*

Corroborated by `docs/MIGRATIONS.md:50`: *"backfill in a separate migration / script that runs in batches outside the Helm hook."* That script also calls the **same production write path** a real sign-up uses rather than bespoke SQL — the right model here too (call the real sync, don't hand-write UPDATEs).

This is consistent with the AGENTS.md rule (request paths never aggregate history; one-time aggregation belongs in a migration): nothing here is a request path, and the "aggregation" is an external API fetch, so the cron/script split is correct.

**Orphaned hollow entities:** if email-first matching re-points members to real people, the old hollow `person` rows are left dangling. The repo has a proper merge facility — `packages/server/src/utils/entity-merge.ts` (`applyMerge`, `merged_into` tombstone + recall redirect, migration `20260707160000_entity_merged_into.sql`). Whether to auto-merge or leave orphans is a product call; auto-merging from a sync tick is riskier than it looks and I'd default to leaving them and cleaning up manually given the volume (see §5).

## Risks

- **Fail-closed regression (highest).** `syncSlackConnectionAcl` is atomic per connection; any throw marks the connection `failed` and the gate drops all its channels (`slack-acl-sync.ts:16-22, 250-261`). A `missing_scope` from `users.list` on every not-yet-reinstalled workspace would silently kill Slack channel visibility fleet-wide until reinstall. Must be caught and swallowed.
- **Identity-order silently decides collapse vs. fork**, with no ambiguity logging in matcher 1 (`access-graph.ts:175-179`). Getting this backwards makes hollow duplicates permanent and is not loud about it.
- **Cross-person leak via a shared/aliased email.** `IDENTITY.EMAIL` is `uniquePerOrg: true`, and email-first matching means a Slack member whose profile email collides with an existing person inherits that person's `member_of` edges. Since these edges are a **read ACL**, a bad collapse is an access-control event, not just a data-quality one. Worth a test.
- **Scope propagation lag** — up to 1 hour for `refresh-connector-definitions` to push the new scope into per-org `connector_definitions`. Installs started before that still mint tokens without `users:read.email`.
- **Reinstall is manual and unprompted** — no detection exists, so workspaces will sit on old tokens indefinitely with no signal to anyone.
