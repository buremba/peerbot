5. **Problem Solving:**

   Established the **screen decomposition** that decides feasibility: 441 screens = **207 config-driven CRUD** (`TanitimSablon` from an `ALANLAR` field table) + **142 hand-coded reports** (`ListeYap.XxxList`) + ~113 real business logic. Prodma already built a schema-driven admin; so has Lobu (0 frontend files per entity type).

   Isolated the **irreducible architectural gaps** via the perfect-agent test. Root cause in one sentence: *Lobu's entity store is a KNOWLEDGE store (current state, org-scoped, mutable); an ERP needs a LEDGER (historical, row-scoped, deterministic, immutable).* Four consequences: (1) no history — `manage_entity` writes no event/audit, no field-version table, `asOf` declared but NotImplemented; (2) no immutability — no frozen state, no `beforeUpdate` hook, no state machine; (3) no row-level scope; (4) no transaction boundary for org code — sandbox read-only, connectors get no DB handle, though an atomic multi-write path exists via Behavior declared-output (data-in, no-code). Plus the sleeper: aggregates need a developer per number.

   **KEY DESIGN INSIGHT surfaced:** storing document lines as a **metadata array** rather than child entities makes header+lines ONE `entities` row = ONE write = **naturally atomic**, dissolving gap (4), shrinking immutability to a single write-gate check and concurrency to a single-row lock. This became question **S1** and everything else hangs off it.

   Identified **Prodma is weaker than its reputation** (lowers the bar): cosmetic field permissions, plaintext passwords, no transactions, MRP stub returning null, broken scheduler, two disagreeing price engines with a `HATALIDIR` comment in source, manual repair tools for posting inconsistency.

   Identified the **generated-UI ceiling**: two registries (`components` and `actions`), both unused — a template can *reference* an action but not *define* one. The **action vocabulary** is the real extensibility surface, seedable from Prodma's 170+ operation codes.
