CONTEXT — the existing state (all verified true):
1. There is a working in-product "replay eval" engine in packages/server/src/runs/ (eval-runs.ts, eval-cases.ts, eval-scores.ts, eval-suite.ts) and a scorer queue (scheduled/score-eval-runs.ts). Flow: a real Behavior run is "promoted" into a $eval_case DB entity (source_run_id + human "expectation"), then replayed as a behavior_eval run under capture mode (executionMode='capture' signed token claim — the agent does the same reads but records side effects to runs.dry_run_preview instead of performing them), then scored by code metrics (completed_window, output_present) + an optional LLM judge against the expectation. A suite runner replays each case N trials (default 3) and readEvalResults compares latest-vs-previous trial-group means, flagging a regression only when the drop exceeds the case's observed spread. Three HTTP routes exist: POST /api/:orgSlug/agents/evals/cases, POST .../behaviors/:behaviorId/evals/run, GET .../behaviors/:behaviorId/evals/results. Integration tests green. BUT: no UI, no ClientSDK methods, no committed eval corpus, no CI gate. The only trigger surfaces are the raw HTTP routes and two ad-hoc bun scripts (scripts/promote-eval-case.ts, scripts/queue-eval-run.ts) whose headers explicitly say the trigger surface "has not had design sign-off".
2. There is also a promptfoo provider (packages/promptfoo-provider) that drives a Lobu agent through the gateway Agent API for conversational evals (committed promptfooconfig.yaml in examples/, but nothing in CI runs them; provider hardcodes dryRun:true on sessions).
3. The CLI (packages/cli) is commander-based and has a generic admin dispatcher: `lobu call <tool>` posts to POST /api/:orgSlug/:toolName, and GET /api/:orgSlug/tools lists the surface. Any tool registered on that surface is reachable from CLI, MCP clients, and the SDK.

THE PROPOSAL being reviewed ("evals as a first-party primitive", corpus-as-code layer over the existing replay engine):
- Register eval actions on the admin tool surface (eval.promote_case, eval.run_suite, eval.read_results, eval.export_case) so CLI/SDK/MCP reach them with no bespoke wiring.

- Server deltas: (a) createEvalRunFromPayload mint (payload instead of sourceRunId) + a code:<caseId> identity scheme; (b) a sync/upsert endpoint for apply; (c) export needs the frozen payload returned from a route (not currently exposed); (d) surfacing readEvalResults' existing regression-vs-spread logic as the `check` gate.

- Owletto UI later (a Behavior detail tab showing per-case latest/previous/spread).
