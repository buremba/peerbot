## Design decisions

### 1. Persistence: a dedicated `agent_package_grants` table (per-agent)

Not `agents.settings.nixConfig` (CLI apply clobbers it; also settings writes race with UI edits) and not org-wide rows (org-wide intent is expressed as *policy*, not grants — an allowlisted package auto-grants for any agent that asks, which gives org-wide behavior without an org-wide grant object). Skill provenance is recorded as a column, not a scope.

```sql
-- db/migrations/&lt;ts&gt;_agent_package_grants.sql
CREATE TABLE IF NOT EXISTS public.agent_package_grants (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  organization_id text NOT NULL REFERENCES public.organization(id) ON DELETE CASCADE,
  agent_id text NOT NULL,
  package text NOT NULL,               -- validated via nixPackageAttrRef before insert
  reason text,
  skill text,                          -- provenance only
  source_run_id bigint,                -- approval run, NULL for auto-approved
  granted_by_user_id text,             -- NULL for policy auto-grants
  granted_via text NOT NULL DEFAULT 'approval',  -- 'approval' | 'auto_policy'
  created_at timestamptz NOT NULL DEFAULT now(),
  revoked_at timestamptz,              -- tombstone; never DELETE
  revoked_by_user_id text,
  CONSTRAINT agent_package_grants_active_key
    UNIQUE (organization_id, agent_id, package, revoked_at)  -- see note
);
```
(Note: a partial unique index `WHERE revoked_at IS NULL` is the cleaner uniqueness; per GOTCHAS squawk conventions it needs `CREATE UNIQUE INDEX IF NOT EXISTS … -- squawk-ignore require-concurrent-index-creation` on the brand-new table instead of the table constraint sketched above.)

Consumption: **source 4 in `resolveAgentOptions`** — after the existing three-way union, read active grants for `(agentId, organizationId)` via a new store (`packages/server/src/lobu/stores/package-grants.ts`, using `getDb()` like the adjacent `provider-secrets.ts` import) and fold into `mergedOptions.nixConfig.packages`. Skip when `organizationId` is absent (declared orgless agents — fail closed, no grant lookup). This automatically covers every scheduled/chat/API run and inherits `NIX_CACHE_DOMAINS` egress granting and `nixPackageAttrRef` validation downstream.

### 2. MCP tool: `request_environment_package`

New file `packages/server/src/tools/request_environment_package.ts`, registered in `AGENT_TOOLS` in `packages/server/src/tools/registry.ts` (visible on tools/list to every worker via the lobu MCP server). No "watcher" anywhere in name/description/schema (naming gate).

```ts
export const RequestEnvironmentPackageSchema = Type.Object({
  package: Type.String({
    description:
      "nixpkgs attribute to add to this agent's sandbox, e.g. 'ffmpeg', 'imagemagick', or 'python3Packages.requests'. Leaf or &lt;namespace&gt;.&lt;leaf&gt; only — no flake URLs, no versions.",
  }),
  reason: Type.String({
    description: "One sentence on why the package is needed; shown on the approval card.",
  }),
  skill: Type.Optional(Type.String({ description: "Skill this dependency supports, if any." })),
});
// Result: { status: 'granted' | 'pending_approval' | 'denied',
//           run_id?: number, event_id?: number, message: string }
```

Handler flow (mirrors `queueWriteForApproval` in `manage_agents.ts:666-820`):
1. Require `ctx.agentId` + `ctx.organizationId` (`ToolContext`, bound from the worker token — `mcp-handler.ts:835`); reject human/anonymous sessions with a pointer to agent settings instead (humans edit settings directly).
2. Validate the name with `nixPackageAttrRef` (import from `@lobu/connector-sdk/nix-package`; server already depends on it) — reject before anything is queued so an un-approvable card never exists (same principle as manage_agents' pre-validation).
3. **Interpreter-gate check** (requirement 6): if the package name (or its known binary aliases, e.g. `nodejs`→`node`) is in the gated set → return `denied` with an explicit message ("full interpreters/network tools are excluded from the sandbox command surface; granting would be a no-op because the worker filters these binaries") — never silently granted, never auto-approved. To share the list, lift `UNSANDBOXED_INTERPRETERS` from `packages/agent-worker/src/embedded/just-bash-bootstrap.ts:79` into `@lobu/core` (e.g. `packages/core/src/contracts/sandbox-exec.ts`, exported as `UNSANDBOXED_INTERPRETER_NAMES`), import it back in the bootstrap (behavior-identical) and in the server handler. Server cannot import agent-worker (not a dependency — verified `packages/server/package.json`), core is shared by both.
4. Resolve the effect via `resolveWriteEffect` (`entity-policy.ts:863`) with the new class/action (below): `auto` → insert grant + audit event, return `granted (available next session)`. `approval` → pending run + card. `deny` → return denied.
5. Pending path: `INSERT INTO runs (… action_key='sandbox_package_install', approval_status='pending' …)` with `idempotency_key = hash('sandbox_package_install|org|agent|package')` + the advisory-lock/find-existing/reuse pattern from `entity-field-approval.ts:750-785` so repeated asks collapse to one card; `insertEvent` with `interactionType:'approval'`; fire `notifyActionApprovalNeeded`; return the "card is shown, stay terse" message idiom (`manage_agents.ts:816`).

Also update the bash deny message at `packages/agent-worker/src/runtime/tools.ts:269` to point agents at `request_environment_package`.

### 3. Policy tiers: new write-gate class `sandbox_package`, action `install`

- `packages/server/src/authz/entity-policy.ts:51`: `WriteResourceClass` += `'sandbox_package'`.
- `packages/server/src/authz/write-action-manifest.ts`: add `install` to `WriteAction`; add class manifest `{ actions: ['install'], effects: ['auto','approval','deny'], defaultEffect: { install: 'approval', …others: 'deny' } }` — approval-gated by default, per requirement 2.
- Migration widening the child-table CHECK (`write_policy_action_effects.action IN (…)`, created in `20260710120000_write_policy_action_effects.sql:49`) to include `'install'`, using the `NOT VALID` + `VALIDATE` two-step from `20260709120000_write_policy_expand.sql` (precedent: `20260713150000_write_policy_entity_read.sql`).
- **Org auto-approve allowlist** = policy rows: `{ resource_class:'sandbox_package', operation_key:'&lt;package&gt;' | NULL, principal_kind/principal_id optional, install → auto }`, reusing `operation_key` as the package scope exactly as `connector_action` scopes per operation. - **Hard floor**: the handler's interpreter-gate check runs *before* policy resolution, so an org allowlist row can never auto-approve a gated interpreter.

### 4. Approval decision + apply

Register a third `BuilderApprovalHandler` in `getBuilderApprovalHandlers()` (`manage_operations.ts:1712`):
```ts
{ actionKey: SANDBOX_PACKAGE_INSTALL_ACTION_KEY, nounLabel: 'Package',
  isValidProposal, apply: applySandboxPackageGrant, describe: p =&gt; `install ${p.package}` }
```
`applySandboxPackageGrant` (in the new tool file) inserts the grant row (`ON CONFLICT DO NOTHING` on the active-uniqueness index) and the audit event. The shared claim path (`claimBuilderRun`, `UPDATE … RETURNING` — multi-replica safe), `supersedeActionEvent` terminal chain, and the expiry sweep all apply with zero new orchestration code.

### 5. Device workers: structural + explicit deny (requirement 2/3)

- Grants live only in `agent_package_grants` → consumed only in `resolveAgentOptions` → `messageData.nixConfig` → embedded gateway spawn. The device poll path (`worker-api/poll.ts:932`) reads `connector_runtime.nix.packages` exclusively; the two channels never touch. Add a regression test asserting a grant for an agent does not alter the poll response for a device-pinned connection.
- Defense in depth: the tool handler denies when the MCP session is not an agent-worker session, and device connector-workers have no MCP tool surface at all (they use `/worker-api`). Document the invariant in `packages/server/AGENTS.md`'s device-pinned section.
- Remote sandbox providers (vercel/e2b/…) currently don't get nix provisioning on main (feat/connector-agent-env branch is unmerged); grants degrade exactly like declared packages do there (warned, unavailable) — no new hazard.

### 6. In-session experience (requirement 4)

- **Phase-1 UX**: the tool result says "granted — available in your next session" (auto) or "queued for approval; available in a later session once approved". Correct with zero orchestration risk, because nix is spawn-time only.
- **Phase-2 (fast-follow) — nix-drift respawn**: at the warm-dispatch site in `message-consumer.ts` (~line 1097 "Existing thread"), compare the payload's `nixConfig.packages` (freshly resolved per message by `resolveAgentOptions`) against the spawn-time `entry.env.NIX_PACKAGES` via a new `DeploymentManager.hasNixDrift(deploymentName, packages)` (the entry shape at `deployment-manager.ts:250` already retains `env`). On drift: `deleteDeployment` → `createWorkerDeployment`. This is pod-local (each pod compares its own process's spawn record against the authoritative Postgres-derived payload — no cross-pod state), runs between turns by construction (the conversation advisory lock serializes turns), and the transcript survives via PG snapshot hydration. Cost: SIGTERM→respawn seconds, plus nix-shell evaluation (fast on warm cache; cold-cache downloads can take tens of seconds — acceptable at turn start, and `NIX_CACHE_DOMAINS` grants are already synced). Mid-turn refresh is **not** feasible and not attempted.

### 7. Audit (requirement 5)

All append-only `events`: request → `interaction_type='approval'` pending event (origin `run_&lt;id&gt;_pending`); decision → `supersedeActionEvent` chain (approved/rejected/expired), reviewer recorded; auto-grants → a non-interactive `semanticType:'operation'` event with `metadata: { action: 'sandbox_package_grant', package, granted_via: 'auto_policy', policy_id }`; revocation → tombstone (`revoked_at`) + a new event, never a delete. MCP tool invocations are additionally captured by the existing tool audit (`packages/server/src/tools/audit.ts`).

## Phased implementation plan

- **Phase 0 (core, no behavior change)**: move `UNSANDBOXED_INTERPRETERS` to `@lobu/core` as `UNSANDBOXED_INTERPRETER_NAMES`; re-import in `just-bash-bootstrap.ts`. Note the three build lists / stale-dist gotchas (`make build-packages` before typecheck).
- **Phase 1 (storage + union)**: migration `agent_package_grants`; store `packages/server/src/lobu/stores/package-grants.ts` (mind `pgTextArray` for any array binds); fold source 4 into `resolveAgentOptions` in `platform-helpers.ts` (biome-excluded — edit surgically); tests alongside the #2218 union tests.
- **Phase 2 (policy class)**: `WriteResourceClass`/manifest additions; CHECK-widening migration (`bun run db:lint` it); REST validation in `index.ts`.
- **Phase 3 (tool + approval family)**: `tools/request_environment_package.ts` + registry entry + `BuilderApprovalHandler` registration + notification + worker deny-message update. Run `make pre-pr` for the naming gate.
- **Phase 4 (freshness, optional)**: nix-drift respawn in `message-consumer.ts` + `deployment-manager.ts`.
- **Phase 5 (UI, paired owletto PR)**: grants list/revoke in agent settings; approval card already renders via the generic interaction envelope.

Rollout: all additive (new table, widened CHECK, new action_key string — `runs.action_key` is free text); no two-phase column dance needed; old replicas ignore the new tool during rollout overlap. Multi-replica correctness rests entirely on Postgres (runs claim, grants table, per-message resolution).

**Risks**: package→binary alias mapping for the interpreter gate is best-effort (worker-side `discoverBinaries` filter remains the hard enforcement — a slipped-through grant is a no-op, not an escape); prompt-injected package requests (mitigated: nixpkgs-attr-only, no flakeUrl, approval default, reason on card); cold-cache nix latency at next spawn; config-as-code drift (grants invisible to `lobu.config.ts`); pending-request spam (idempotency collapses dupes; consider a per-agent pending cap).

**Open product questions**: (1) should "Approve" offer an "always allow for this org" that also writes the allowlist policy row? (2) grant expiry/review UI? (3) gated-interpreter requests: flat deny (proposed) vs escalate to operator, since `LOBU_ALLOW_UNSANDBOXED_EXEC` is a deployment-level knob no org admin can approve? (4) auto-revoke skill-provenance grants when the skill is disabled? (5) proactively wake the conversation on approval vs discover-next-turn?
