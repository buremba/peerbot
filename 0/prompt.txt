## 5. Problem Solving

**The central reframe.** The user's question — "isn't events suited for this use-case" — turned out to be the direction the codebase had already been travelling. Investigation established:

1. **The per-key cursor exists.** `watcher_windows` was deleted and replaced by canvas chains; the chain-root partial unique index is an O(1), non-aggregating, multi-replica-safe keyed slot. Changing the third key column generalizes it to per-entity fan-out with zero extra `watchers` rows — which would delete `create_from_version`, `watcher_group_id`, per-assignment `sources[]`, and `{{entityId}}` together, since `{{entityId}}` exists only to let one stored source serve N cloned rows.
2. **The durable step engine exists.** `runs` has the full queue column set plus a real `runs_idempotency_key_uniq`. A step is a run row.
3. **The fingerprint read is genuinely unindexed** — a per-Behavior history sort each tick with no covering index — but has zero users, so it's latent.

**Then the spikes inverted the recommendation.** Prod (org 8dc12bdd, read-only) shows:
- 67 Behaviors; 66 distinct `watcher_group_id`s; **exactly one group (id 45) with 2 members** — fan-out used once ever
- **0** Behaviors using `{{entityId}}`; **0** using `{{organizationId}}`; **0** using `skip_if_unchanged`
- **12** with a `reaction_script` (the only advanced surface with real adoption); 59 with sources; 4 active; 3 with entity scope
- events_total 350,277; `audit` = 165,628 = **47.29%**, 100% of it `origin_type='tool_invocation'`
- canvas: **90 rows, 86 roots, 4 supersedes** — a 4.7% revision rate, so the pattern has never been tested under churn
- 4,861 live entities (the fan-out multiplier)
- Per-day rates: content flat ~2,100/day; audit 0 → 10 → 98 → 1,441 → **16,819**/day (Apr→Aug), an order of magnitude per month. August is a 7-day window so the last bar may be a burst.

**Conclusion delivered:** delete rather than migrate. The fan-out machinery needs a deletion PR, not an architecture. Grow the reaction-script seam (12 users) using the already-proven primitives, when demand appears. Keep cursors out of `events` unless the churn question is settled — the counter-precedent is `feeds.checkpoint jsonb`, a mutable slot solving the structurally identical "what's new since last time per source" problem at higher volume.
