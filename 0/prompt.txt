## 3. Verdicts

**Q1 — Rule, not structure. But corrections are new *documents*, not superseded *versions*.** The `events.supersedes_event_id` pattern exists precisely because `events.id` is a stored-version id, not identity. `entities.id` is the opposite: it IS the identity everything points at — `entity_relationships`, `events.entity_ids`, `x-link-entity-type` references, and the `merged_into` forwarding machinery (whose cost across the codebase shows what pointer-chasing buys you). A generic entity-supersede mechanism re-keys the invoice and orphans or forwards every reference. Meanwhile the domain already answers this: Turkish e-invoice practice (and accounting generally) forbids editing a posted invoice and mandates correction via a *new* document — cancellation or return/corrective invoice. So: WP-2's gate freezes the row in place; a correction is a new document entity linked to the original via `entity_relationships`. You get append-only semantics at the domain layer using only existing machinery, and no new versioning mechanism — which the "Coordination design brake" invariant would tell you to refuse anyway. One caveat the rule approach owes: the approval-apply path **bypasses the gate** — `applyEntityFieldChangeProposal` (`entity-field-approval.ts:1085-1121`) writes via `mergeEntityFields` directly, so an agent proposal queued pre-posting and approved post-posting writes into a frozen doc. The freeze check must live at the write chokepoint (inside updateEntity's tx / mergeEntityFields), not only in the gate pipeline.

**Q2 — Per-entity-type opt-in.** Global in-tx audit changes the failure semantics of every existing write path (memory updates, person merges, connector-driven entity writes) from "write succeeds, audit best-effort" to "audit failure aborts the business write" — a platform-wide behavior change smuggled in for a PoC. Fail-closed is exactly right for financial documents and consistent with the "fail closed on durable state" invariant, but that invariant doesn't demand it for a memory-note edit. The opt-in flag also rides the same entity-type-data vehicle WP-2 already builds, so it's one config surface, not two. (Both the flag and WP-4's version column are DB design changes — per AGENTS.md they require explicit user confirmation before anyone builds them.)

**Q3 — Stage 1 yes (it's nearly free), stage 2 no (wrong shape).** Derived `backing_sql` entity types already exist end-to-end — executor (`entity-management.ts:70-135`), path resolution and measure inference (`resolve_path.ts:888-926`), UI that skips `x-measure` columns (`dynamic-schema-form.tsx:199`). Stage 1 is close to zero new code. But stage 2 — teaching `metrics/compiler.ts` an entities source — is the wrong latent shape. The repo's own invariant prescribes the alternative: *materialize the row or counter at WRITE time and read it back by index*. WP-1's in-tx work already gives you the vehicle: roll period totals into a stats entity row updated in the same transaction as the document write. That's a fraction of the compiler work, respects the invariant directly, and the compiler stays events-native. Also remember this is a gap-finding PoC: the compiler's v1 scope comment (`compiler.ts:14-15`) already *documents* the gap; building the fix is doing the migration you said you weren't doing.

## 5. Ordering, and the human short-circuit

**The short-circuit is load-bearing; do not "open" it.** The entire field-ownership system is built on the premise that human writes are final: `evaluateEntityFieldUpdates:1000-1007` makes any human-owned field `require_approval` *unconditionally* — that rule only makes sense because the caller is never human. Route human updates through today's semantics and every human edit of a field a human previously set queues an approval card **to themselves**. Likewise `affirm_fields` (human-claims-ownership, `entity-management.ts:596`) and `applyEntityFieldChangeProposal` writing `source: "human"` all assume human authority terminates the loop. The correct move is narrower: invoke `runMutationGate` for human edits in updateEntity, but leave `entity-policy.ts`'s user-allows untouched — the approval interceptor keeps returning allow for users, and the new data-driven interceptor is a *separate* rule class (state machine / frozen) that denies regardless of `principalKind`. The gate pipeline already folds multiple interceptors (`entity-mutation-gate.ts:241-260`); no entity-policy change is needed at all. Plus enforce frozen at the write chokepoint so the approval-apply path can't bypass it.

**Ordering:** mostly fine, two changes. (a) WP-2's entity-type config vehicle must land before WP-1's per-type opt-in flag — both need per-type config storage; build it once. (b) Insert a WP-0 decision on row-level read authz before WP-3/WP-5, because the lookup picker and derived views both leak rows if it's deferred silently. WP-4 is independent and can go first — it's the cheapest and de-risks the JSON-lines lost-update problem that everything else assumes away.
