CONTEXT
Lobu models permissions as edges in entity_relationships. A locked design (docs/plans/authz-acl-permission-program.md) extends this: principals=entities, memberships=member_of edges, ACLs=can_read/deny_read edges, one SQL gate. can_read/deny_read are NOT built.

I surveyed industry fit and found six structural gaps, all failing for the same reason — they are not expressible as edge EXISTENCE:
 - field/column-level access (healthcare, HR salary)
 - intersectional rules A AND B (finance information barriers, Jira browse AND issue-security) — allow-edges are disjunctive under an EXISTS gate
 - deny/exclusion (ethical walls)
 - temporal (access expires)
 - purpose limitation / consent (GDPR, healthcare)
 - classification lattices (government) — dominance, not reachability

PROPOSAL: a two-layer model — 'facts + rules'.
 Layer 1 (exists): the graph = indexed reachability facts, narrows candidate rows by index.
 Layer 2 (new): a policy expression over reachability + entity attributes + request context, COMPILED INTO A SQL PREDICATE plus a column projection. Not compiled into data.
Claim: each of the six gaps becomes a one-line condition (a && b; forbid when...; when now() < expires_at; when ctx.purpose == X; projection for fields; subj.clearance >= obj.label).
Claim: this is CHEAPER than the locked plan's 'compile intersections to synthetic effective principals at write time', because synthetic principals must be recomputed on every membership change in either input group, whereas read-time evaluation is two index lookups.
Claim: Lobu already has this seam — authz/connection-visibility.ts compileConnectionFkVisibility/compileConnectionRowVisibility, utils/execute-data-sources.ts buildScopedQuery, and a CI lint guard scripts/check-connection-visibility-compiler.mjs that bans re-deriving the gate outside the compiler.
