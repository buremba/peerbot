My 3 merge tests went green. Then the regression sweep:

```
 FAIL  manage_entity merge action &gt; auto-merges an exact configured email match without human approval
   ToolUserError: Merge failed: Policy denied deleting entity 101
 FAIL  manage_entity merge action &gt; discovers duplicate groups server-side from candidate IDs
   ToolUserError: Merge failed: Policy denied deleting entity 103
```

**Why it is structural.** `WRITE_ACTION_MANIFEST.entity.defaultEffect.delete` is `"approval"` (`src/authz/write-action-manifest.ts:64`). Every merge tombstones its loser, so gating the merge as a `delete` makes the approval interceptor demand approval for *every agent/watcher auto-merge* under default policy — and a merge transaction cannot express a defer: it is one atomic fuse plus an undo ledger, with no post-commit hook. Worse, the question is already answered upstream: `handleMerge` runs `assessEntityResolution` and routes `review` to `proposeEntityMerge`, a merge-specific approval card. Reaching `applyMerge` means approval is settled; re-asking the approval interceptor double-gates with a mechanism that already ran.

The missing capability is in the gate, not in `entity-merge.ts`: **`runMutationGate` runs an undifferentiated interceptor list and folds approval and data rules into one verdict.** There is no way to say "approval is already decided, run only the data-rule interceptors." Splitting them (interceptor categories, or a `policyAlreadyDecided` flag) changes the gate's public contract, which per AGENTS.md needs a surfaced proposal first. So I stopped, per your instruction.

I deliberately did **not** ship the winner-update half alone (it gates cleanly — entity `update` defaults to `auto`, no regression). Landing half would have left the loser-tombstone hole open behind a suite that reads as comprehensive, and would have meant accepting the double-gate on `update` while rejecting it on `delete` purely because one broke tests. That is motivated reasoning, not a design.
