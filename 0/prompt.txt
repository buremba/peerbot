## 2. Proposal / review model — and the hollow-entity verdict

**Candidate generation requires a SHARED normalized rule key. A hollow `person` shares none. It is structurally invisible.**

- `packages/server/src/entity-resolution/discovery.ts:71-88` builds `ownersByIdentity` keyed on `${rule.normalizer}:${rule.fields}:${value}` and only `union()`s candidates that land on the **same key** (`:84-88`). `:100-102` then keeps only components of size &gt; 1. A candidate with zero rule keys is a singleton and is dropped.
- The rules come from `readEntityResolutionRules` (`policy.ts:148`). With no `x-lobu-resolution` on the type, `person` falls back to `DEFAULT_PERSON_RESOLUTION_RULES` (`policy.ts:73-78`) = **email / emails / phone / phones only**, all `onMatch: "review"`.
- `normalizedResolutionRuleKeys` (`policy.ts:201-225`) reads metadata path `field` **and** identity rows whose `namespace === field` (`:213-215`). A hollow Slack person has metadata `{display_name:'T…:U…', slack_user_id:'T…:U…'}` (`access-graph.ts:191-193`) and one identity in namespace `slack_user_id`. Neither matches `email`/`phone` → `values.length === 0` → early `return []` at `policy.ts:218`.

**So: today a hollow `T…:U…` person produces zero resolution keys, is never grouped, and can never be proposed.** Even if it were hand-fed as a loser, `assessEntityResolution` yields empty evidence and `allLosersHaveAutoMatch === false` → `decision: "review"` (`policy.ts:295-298`) with reason "No matching email or phone could be verified automatically."

`resolution_keys` = a per-entity readable snapshot of those normalized rule keys, grouped by rule label (`policy.ts:307-322`). It is stored with the proposal so approval-time re-checking can tell "new proof appeared" from "the underlying identities changed."

Approval semantics (`entity-field-approval.ts:1171-1216`): on approval the fingerprint is recomputed (`assertResolutionFingerprintCurrent`); a mismatch is fatal **unless** `hasMergeEvidenceStrengthened` passes. That helper (`evidence-strength.ts:45-105`) requires (a) nothing the reviewer saw disappeared, (b) at least one new evidence item, and (c) **every newly appeared resolution key is matched by a counterpart on the other side** (`:93-101`) — an unmatched new key fails closed, because unmatched keys produce no evidence and would silently widen a merge nobody reviewed.

Verified in code.

## 3. Does merge preserve `member_of` ACL edges? — **Yes.**

`entity-merge.ts` handles relationships generically (no relationship-type filter, so `member_of` is included):

- `:290-316` — first tombstones loser edges that would become self-loops **or** collide with an existing winner edge on `(relationship_type_id, from, to)`. This is a *dedupe*, not a loss: the winner already has that edge.
- `:319-328` — repoints all remaining live edges: `from_entity_id`/`to_entity_id` → winner, `RETURNING id` counted as `repointedEdges`.
- `:229-242` / `:387-404` — before/after snapshots persisted into the `entity_merge_operations` ledger so unmerge restores endpoints exactly.

So a merge does **not** revoke channel visibility. The loser's `member_of` edges land on the winner, deduped against edges the winner already had. `entities.name` of the winner is never overwritten (`:278-284` updates only `metadata` + `field_controls`); the loser's name is folded into `metadata.aliases` (`merge-state.ts:65-73`), so `T…:U…` becomes an alias on the real person.

Verified in code (not exercised against a DB in this session).

## 4. Does the 15-minute sync undo the merge? — **No. Rule this failure mode OUT.**

The sync is `packages/server/src/scheduled/jobs.ts:194-198`, `authz-acl-sync`, cron `*/15 * * * *` → `runAclSyncTick` → `slack-acl-sync.ts:238` `buildAccessGraph`.

The reason it is stable:

- `applyMerge` step 1 (`entity-merge.ts:252-261`) **moves every live `entity_identities` row** from loser to winner (`SET entity_id = winner ... WHERE entity_id = loser AND deleted_at IS NULL`). The `slack_user_id` row now *belongs to* the winner.
- `resolveMembers` (`access-graph.ts:159-166`) looks identities up by `(organization_id, namespace, identifier)` with `deleted_at IS NULL` **on the identity row only** — it never joins `entities`, so it never sees `merged_into` or the tombstone. It gets the winner's id back.
- The `member_of` insert is `ON CONFLICT (from,to,type) WHERE deleted_at IS NULL DO NOTHING` (`access-graph.ts:365-378`), and the winner is in the `keep` set for the departure reconcile (`:391-404`). Nothing re-creates the hollow entity.
- The create path is also protected independently: `lookupMatches` (`entity-link-upsert.ts:353-363`) joins `entities` and filters `e.deleted_at IS NULL`, and the global live-unique index on `(org, namespace, identifier)` makes a duplicate identity row impossible — a lost create race is hard-deleted and re-resolved (`entity-link-upsert.ts:851-878`).

**Latent bug I found while checking this (adjacent, not caused by merge):** `resolveMembers` has *no* `entities` join at all. If a member's entity is soft-deleted by an ordinary `delete` (no merge, so identities are **not** moved), the identity row survives and `resolveMembers` will hand back a **deleted entity id**, write `member_of` edges to it, and never mint a replacement. `lookupMatches` guards this; `resolveMembers` does not. Verified by reading; not reproduced.

## 5. The gap list

**What merge DOES solve for the Slack case**
1. It is a safe, reversible, ledger-backed way to fold an already-forked hollow person into a real one, including `member_of` edges — no ACL regression (§3).
2. The fold is durable against the 15-minute re-sync (§4).
3. It gives a human review surface and an approval trail (`entity_merge_operations`, unmerge, merge-approval card).

**What merge does NOT solve**

1. **It never fires for this case.** Zero rule keys → never grouped, never proposed (§2). Merge is only reachable by a human manually picking two ids, or by an agent hand-picking them. There is no path from "hollow `T…:U…` person exists" to "someone is asked about it."
2. **It cannot cross entity types.** `entity-merge.ts:210-214` throws on `entity_type_id` mismatch. The most common real duplicate here is hollow `person` vs the signed-in human's **`$member`** entity — that merge is *impossible*, at any privilege level. The `duplicate-merge` template compounds this: its source is `@entity:person` (`behavior-templates.ts:145`), so `$member` is never even a candidate.
3. **It's O(n) manual work that regrows.** Merge is cleanup for entities that already forked. Every new Slack member in every newly-synced channel forks a fresh hollow person on the next tick. Merge never closes the tap.
4. **It cannot fix a wrong resolution — only a duplicate one.** `resolveMembers` (`access-graph.ts:173-184`) takes the **FIRST** identity hit in `m.identities` array order, ignores `primary`, and has no ambiguity detection. Once email is added as a second Slack member identity, a stale/shared `email` row can win over `slack_user_id` and attach a channel's ACL edge to the *wrong* person. That is a mis-grant, and merge is not the remedy — unmerge would be, and only after someone notices. Note the contract at `packages/connector-sdk/src/acl-source.ts:30-33` explicitly promises "`primary` ones additionally govern creation," which `entity-link-upsert.ts:756-781` honors and `resolveMembers` does not. GitHub already ships two member identities (`packages/connectors/src/github-identity.ts:128-131`), so this first-hit path is already live, not hypothetical.
5. **Email enrichment is a precondition for merge to ever become useful here, not an alternative to it.** If the enrichment writes the Slack member's email into the hollow person's metadata (or as an `email`-namespace identity), the entity *becomes* discoverable to `discovery.ts` and would then group with a real `person` carrying the same email — decided as `"review"` under the default rules, i.e. queued for a human. That is the correct order of operations: enrich first (so collapse happens at write time and merge becomes a rarely-needed backstop), not merge first.
6. **`$member` has no `email` identity row.** `packages/server/src/utils/member-entity.ts:99-144` stores the member's email in `metadata[emailField]` and writes only an `auth_user_id` identity. The only writer of a `namespace='email'` identity I found is the Gmail connector rule (`packages/connectors/src/google_gmail.ts:200`); `save_content.ts:305-330` only *reads* one as a backfill probe. So an `email`-namespace lookup in `resolveMembers` will typically **miss** signed-in `$member` entities and hit `person` entities instead — the exact collapse the Slack work wants may not happen without also writing an `email` identity at member provisioning. **This is the finding I'm least certain of** — I verified the writers by grep, not by inspecting prod rows.

**Verdict:** merge is a cleanup for cases that slipped through. It is not a substitute for getting the identity ordering right at write time, and for the dominant Slack case (`person` vs `$member`) it is not even available.
