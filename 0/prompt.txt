# Lobu Connectors: Fact Sheet

## 1. Connector anatomy

**Definition model.** Every connector is a default-exported class extending `ConnectorRuntime` (`/Users/burakemre/Code/lobu/packages/connectors/AGENTS.md:6`), or the functional sugar `defineConnector(spec)` which "LOWERS to a real `ConnectorRuntime` subclass so the existing connector-worker runs it unchanged" (`/Users/burakemre/Code/lobu/packages/connector-sdk/src/define-connector.ts:1-28,185`). Built-ins live in `packages/connectors/src/*.ts`; user-authored connectors are `*.connector.ts` compiled from a project dir via `lobu apply` with esbuild bundling npm deps (`packages/connectors/AGENTS.md:6-10`).

**The contract** (`/Users/burakemre/Code/lobu/packages/connector-sdk/src/connector-types.ts`):
- `ConnectorDefinition` (line 21-91): `key`, `kind: 'data' | 'integration'` (line 40 — `'integration'` = "a pure app/auth declaration (e.g. Slack)... NO `feeds` and NO `sync()`"), `authSchema`, `feeds`, `actions`, `behaviorEvents`, `webhook`, `requiredCapability`, `runtime` (device platforms + `nix.packages`, lines 83-110).
- **Feeds (data in)**: `FeedDefinition` (line 419-486) — scheduled `sync()` pulls into the append-only `events` table with a checkpoint; `virtual: true` feeds (line 440-450) are "read LIVE against the source... NEVER synced — no events are persisted". Feeds declare `eventKinds` with declarative entity `attributions` (line 472-515) that link events into the identity graph. Optional per-feed `webhook` routing with `'trigger' | 'store'` modes (line 452-471).
- **Actions (data out)**: `ActionDefinition` (line 589-616) — `requiresApproval: boolean` (597), `kind?: 'read' | 'write'` (599), `requiredScopes` beyond the auth grant (601-604), MCP `annotations` (destructiveHint etc., 606-611), input/output JSON Schemas.
- **Reactions**: reaction scripts belong to Behaviors, not connectors — connector-sdk only holds the context types: "The runtime SDK reaction scripts call is `ClientSDK` (defined in `packages/server/src/sandbox/client-sdk.ts`); only the context shape is shared" (`/Users/burakemre/Code/lobu/packages/connector-sdk/src/reaction-sdk.ts:1-8`). A reaction has shape `default async (ctx: ReactionContext, client, params?)` (line 18-19).

**Real built-ins** (from `/Users/burakemre/Code/lobu/packages/connectors/src/`: github, slack, google_gmail, google_calendar, postgres, jira, linear, discord, telegram, whatsapp, teams, gchat, reddit, rss, x, youtube, hackernews, producthunt, webhook, microsoft_outlook):
- **Gmail** (`google_gmail.ts:95-125`): OAuth (provider `google`, `gmail.readonly` + `gmail.compose`), `threads` feed, actions `send_email`, `create_draft`, `reply` (write) and `search`, `get_thread` (`kind: 'read'`), plus live virtual-feed pushdown (line 484-487).
- **Slack** (`slack.ts:12-19,78-79`): `kind: "integration"` — app_installation auth + declarative webhook verify ("Verify is FULLY DECLARATIVE — the generic engine computes Slack's `v0:{ts}:{rawBody}` HMAC straight from this schema"), no feeds, no sync; chat traffic goes to the chat adapter.
- **Postgres** (`postgres.ts:331-356`): `env_keys` auth with a `DATABASE_URL` field, `query` feed (read-only SELECT sync into events) which also works as a virtual feed.
- **X/Twitter** (`x.ts:1879-1884`): dual auth — OAuth 2.0, plus `type: "browser"` fallback: "browser-based scraping via the paired Owletto Chrome extension... Rides the user's signed-in x.com session; required for the home-timeline feed".

## 2. Auth models &amp; credential storage

**Six auth method types** (`connector-types.ts:220-226`): `none`, `env_keys` (API keys/DSNs, connection- or org-scoped), `oauth` (user-scoped, with `clientIdKey`/`clientSecretKey` for BYO OAuth apps, line 271-272), `browser` (capture `'cli'` — cookies from Chrome profile — or `'cdp'`, line 296-312), `interactive` (QR/pairing-code flows, e.g. WhatsApp, line 282-294), `app_installation` (org/workspace-scoped GitHub App/Slack app/Jira site installs, line 314-327).

**Managed vs BYO OAuth**: managed connectors live in a public org with a managed `oauth_app`; "The managed client secret + refresh token stay in the cloud and never leave it... ONLY the access token + expiry are returned" to a local instance via `POST /oauth/connection-token` (`/Users/burakemre/Code/lobu/packages/server/src/connect/connection-token-route.ts:1-23`). BYO = the connector's declared `clientIdKey`/`clientSecretKey` env pair (`google_gmail.ts:115-116`).

**Storage &amp; encryption**: credentials in `auth_profiles.auth_data` are stored as `secret://` refs into `agent_secrets`, "whose store already encrypts with AES-256-GCM and scopes rows per organization" (`/Users/burakemre/Code/lobu/packages/server/src/utils/auth-credential-secrets.ts:1-16`; `PostgresSecretStore` at `/Users/burakemre/Code/lobu/packages/server/src/lobu/stores/postgres-secret-store.ts:3`). Core crypto is AES-256-GCM with a 96-bit nonce and a strictly-validated 32-byte `ENCRYPTION_KEY` (base64/base64url/hex, round-trip-checked — `/Users/burakemre/Code/lobu/packages/core/src/utils/encryption.ts:3,24-64`). `LOBU_ALLOW_EPHEMERAL_ENCRYPTION_KEY=1` makes the gateway generate a throwaway key for local dev (`/Users/burakemre/Code/lobu/packages/server/src/lobu/gateway.ts:132-150`); otherwise boot fails fast (`/Users/burakemre/Code/lobu/packages/server/src/auth/install-operator.ts:51`). An AWS Secrets Manager backend also exists (`/Users/burakemre/Code/lobu/packages/server/src/gateway/secrets/index.ts:1-5`). There's also a per-sandbox BYO vault for runtime providers that fails closed with "no system-env fallback" (`/Users/burakemre/Code/lobu/packages/server/src/gateway/runtime/credentials.ts:7-23`).

## 3. THE invariant: workers never see real credentials

Root statement: `/Users/burakemre/Code/lobu/AGENTS.md:15`; refined in `/Users/burakemre/Code/lobu/packages/server/AGENTS.md:28-30`: "Workers never see real credentials. The gateway secret/MCP proxies swap placeholders or inject OAuth/API credentials at egress."

**The mechanism, end to end:**
1. **Placeholder mint (gateway-side, at worker spawn)** — `injectSecretPlaceholders` in `/Users/burakemre/Code/lobu/packages/server/src/gateway/orchestration/deployment-manager.ts:1408-1490`: provider credential env vars become `"lobu-proxy"` or a provider-built placeholder (line 1437-1452); any other secret env var is moved into the secret store and replaced by `lobu_secret_&lt;uuid&gt;` via `generatePlaceholder` (line 1454-1476).
2. **The swap seam** — `SecretProxy` in `/Users/burakemre/Code/lobu/packages/server/src/gateway/proxy/secret-proxy.ts:346-355`: "Workers receive random placeholder tokens instead of real secrets. This proxy intercepts requests, swaps placeholders back to real values in auth headers, and forwards to the upstream API." Prefix constant at line 27; the actual swap at `swap()` line 624-661 (fails closed to an empty string so the placeholder never leaks upstream). Placeholders are org-pinned and agent-pinned: `lookupPlaceholderMapping` rejects cross-tenant lookups (line 190-233) and the URL `/a/{agentId}` must match the placeholder's minted agent (line 768-787). Failed resolutions are rate-limited per source (line 54-55).
3. **Forced egress path** — workers can't bypass the proxy: "workers are spawned as child processes of their owner pod and always proxy through `HTTP_PROXY=127.0.0.1:8118`" (secret-proxy.ts:113-117); on Linux the systemd scope's `IPAddressDeny=any` / `IPAddressAllow=127.0.0.1` depends on the proxy binding loopback (`packages/server/AGENTS.md:46`).
4. **App-install tokens** — same invariant, stated in the type contract: "The credential is minted/refreshed gateway-side and never handed to the worker as a raw token — the worker receives a `lobu_secret_&lt;uuid&gt;` placeholder that the secret-proxy swaps at egress" (`connector-types.ts:320-323`); "the private key, the App JWT, and the provider token exchange ALL stay gateway-side" (`/Users/burakemre/Code/lobu/packages/server/src/gateway/installation/installation-token-provider.ts:5-11`).
5. **The exception (and an important nuance)** — credential delivery on run claim, `/Users/burakemre/Code/lobu/packages/server/src/worker-api/poll.ts:877-887`: "trusted/anonymous fleet workers always resolve connection credentials; a user-scoped device worker only gets real credentials when the run's connection is *explicitly pinned to a device* (`connections.device_worker_id`), which was authorized at bind time." So the invariant is about **agent workers** (LLM-driven); the first-party **connector-worker fleet** is a trusted platform component that receives resolved connection credentials to run vetted connector code, and **device workers** (user machines) get creds only for connections pinned to that exact device.

## 4. Sandboxing

- **Connector code** runs out-of-process: the connector-worker daemon polls the gateway, then forks a subprocess that "Receives compiled connector code + an ExecutorJob via IPC" (`/Users/burakemre/Code/lobu/packages/connector-worker/src/executor/child-runner.ts:1-7`). Honest caveat in-code: "Node subprocess execution is process isolation, not a security sandbox" (`subprocess.ts:207-208`). Native deps are provisioned via `nix-shell -p` with injection-hardened package refs ("`nix-shell -p` evaluates each argument as a Nix expression, so a raw value could run arbitrary code" — `subprocess.ts:221-225`).
- **DB egress guard** (`/Users/burakemre/Code/lobu/packages/connectors/src/db-egress-guard.ts:1-42`): two policies, `allow-private` (self-hosted) vs `block-private` (cloud); under block-private it does "resolve-then-PIN" (socket dials exactly the validated IP, closing DNS rebind) and "forced TLS: `sslmode=disable` is rejected outright". The policy is gateway-authoritative, shipped as a top-level claim field so "block-private can never be downgraded" (`poll.ts:946-957`), and tenant config can never override it (`GATEWAY_AUTHORITATIVE_CONFIG_KEYS`, `child-runner.ts:24-45`).
- **Cloud gates** (`/Users/burakemre/Code/lobu/packages/server/src/utils/connector-cloud-gate.ts:22,38`): `CLOUD_RESTRICTED_CONNECTOR_KEYS` is currently an empty holding pen ("postgres graduated"); `DB_EGRESS_HARDENED_CONNECTOR_KEYS = {'postgres'}` — in cloud mode a fleet worker may only claim such runs if it advertises the `db_egress_hardening` capability (`poll.ts:448-461`).
- **Agent workers**: subprocesses under `./workspaces/{agentId}/`, wrapped in `systemd-run --user --scope` on Linux, `LOBU_REQUIRE_WORKER_SANDBOX=1` to enforce (`packages/server/AGENTS.md:47`); HTTP(S) egress via the authed proxy plus `WORKER_ALLOWED_DOMAINS`/`WORKER_DISALLOWED_DOMAINS` (line 46). Nix-provided binaries are exposed as tools, but `UNSANDBOXED_INTERPRETERS` (node, python, bash, curl, ssh, nix, npm, cargo, go, ...) "are filtered out unless the spawned worker has `LOBU_ALLOW_UNSANDBOXED_EXEC=1`" (`/Users/burakemre/Code/lobu/packages/agent-worker/src/embedded/just-bash-bootstrap.ts:79-143`).
- **Vercel sandbox** exists as a gateway runtime provider (`@vercel/sandbox` microVMs, remote workspace at `/vercel/sandbox` — `/Users/burakemre/Code/lobu/packages/server/src/gateway/runtime/providers/vercel.ts:1-11`) for agent runtime execution, not for connector sync runs.

## 5. Privacy / visibility

- **Per-connection visibility** (`/Users/burakemre/Code/lobu/packages/server/src/authz/connection-visibility.ts:1-58`): one compiler for every read seam (query_sql, recall, get_content). "a connection is visible when `visibility = 'org'` OR it is the principal's own private connection (`created_by = principal`). A `null` principal (headless / service) sees only org-visible connections." The FK form gates any table with `connection_id` — so events from a private connection are excluded from other members' queries at the SQL predicate level (line 42-58).
- **oauth_account defaults private, enforced twice**: "an `org`-visible connection on a personal credential exposes that user's private data to every org member" — `isPersonalCredentialKind` = `oauth_account` only (`/Users/burakemre/Code/lobu/packages/server/src/tools/admin/helpers/connection-helpers.ts:592-607`), backed by a DB trigger (migration `20260703200000_connection_personal_cred_private_guard.sql`, referenced at line 610-614) raising "A personal-credential (oauth_account) connection cannot be org-visible". This is exactly how one member's Gmail doesn't leak via agent recall: the Gmail connection is oauth_account → forced private → its events fail the visibility predicate for everyone but the owner. Test: "an OWNER's oauth_account (personal-login) connection defaults to PRIVATE" (`connection-visibility-default.test.ts:86`).
- **Per-resource visibility** (`/Users/burakemre/Code/lobu/packages/server/src/authz/resource-visibility.ts:1-35`): a second gate ANDed on top, keyed on ACL graphs synced from the source (GitHub repos, Linear teams). Three-state: never-graphed connection → passthrough to the connection gate; enforced (fresh ACL) → visible only if requester is `member_of` the resource entity; graphed-but-stale → **fails closed**: "a stalled sync hides data, it does not leak it" (line 27).

## 6. Approvals / write gate

An agent's outbound connector action is gated at three layers that compose restrictively. First, the action's own declaration: `requiresApproval` on `ActionDefinition` (`connector-types.ts:596-597`), and OpenAPI-derived operations auto-classify every non-GET as `kind: 'write'` with `requiresApproval = true` (`/Users/burakemre/Code/lobu/packages/server/src/operations/connector-operations.ts:330-331`). Second, at execute time (`/Users/burakemre/Code/lobu/packages/server/src/tools/admin/manage_operations.ts:1043-1110`) the server resolves the acting principal (agent vs Behavior) and consults the generalized write gate — "Org-level connector-action policy, from the SAME write-gate the entity and agent_config classes use... a `deny` blocks outright; an `approval` upgrades a connection that would auto-run to queued" — via `resolveWritePolicyDecision` with `resourceClass: "connector_action"`, `action: "execute"`, and a connector-qualified per-operation key (e.g. `deliveroo::place_order`). The legal action/effect vocabulary (`auto | approval | deny | disabled`) lives in the write-action manifest, which fails closed on any row the build no longer declares (`/Users/burakemre/Code/lobu/packages/server/src/authz/write-action-manifest.ts:1-33`). Third, the queue enforces the verdict structurally: a queued run is written `status='pending', approval_status='pending'` atomically with its approval event (`/Users/burakemre/Code/lobu/packages/server/src/runs/queue-service.ts:872-905`, `manage_operations.ts:1112-1121`), and the worker claim SQL only ever selects `approval_status = 'auto' OR 'approved'` (`poll.ts:436`) — an unapproved action is unclaimable by any worker. Undecided approvals expire (distinct from human rejection, "an agent must not train on silence as if it were disapproval" — `connector-types.ts:666-677`). MCP-side, unannotated tools require approval by conservative default (`/Users/burakemre/Code/lobu/packages/server/src/gateway/permissions/approval-policy.ts:1-35`). This generalized gate is the #1827 "write-gate generalization" lineage (per project memory).
