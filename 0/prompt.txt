- **`packages/server/src/gateway/connections/state-adapter.ts`** (THE FIX, worktree `chat-state-expiry-reclaim`)
  - Root cause of production message loss. `setIfNotExists` blocked on row existence, not validity.
  - Before: `ON CONFLICT (key_prefix, cache_key) DO NOTHING RETURNING cache_key`
  - After (+26/-1 including docblock):
```js
  /**
   * Claim `key` iff it is not currently held — where "held" means present AND
   * unexpired. Both callers are TTL-bounded claims: the Chat SDK's inbound
   * dedupe (5-minute window) and `claimThreadBackfill` (24-hour window, whose
   * own docstring promises "at most once per thread per TTL window"). A lapsed
   * claim must therefore be re-acquirable.
   *
   * A bare `ON CONFLICT DO NOTHING` blocks on the row's EXISTENCE, not its
   * validity, and expired rows are only swept opportunistically inside `get()`
   * — which this path never calls. That turned every TTL here into "once,
   * permanently": a Telegram message id claimed by one bot silently discarded a
   * different bot's message months later, since ids restart at 1 per bot chat.
   *
   * Mirrors `acquireLock` above; this was the one TTL-bounded claim in the file
   * not already written that way.
   */
  async setIfNotExists(key, value, ttlMs?): Promise<boolean> {
    this.ensureConnected();
    const serialized = JSON.stringify(value);
    const expiresAt = ttlMs ? new Date(Date.now() + ttlMs) : null;
    const rows = await this.sql<{ cache_key: string }>`
      INSERT INTO chat_state_cache (key_prefix, cache_key, value, expires_at)
      VALUES (${this.keyPrefix}, ${key}, ${serialized}, ${expiresAt})
      ON CONFLICT (key_prefix, cache_key) DO UPDATE
        SET value = EXCLUDED.value,
            expires_at = EXCLUDED.expires_at,
            updated_at = now()
        -- Expired rows are logically absent. A live row fails this guard, so
        -- nothing is updated and RETURNING is empty: the caller sees false and
        -- the stored value is untouched. A NULL expires_at (never expires) also
        -- fails it, since NULL compared to now() is NULL rather than TRUE.
        WHERE chat_state_cache.expires_at <= now()
      RETURNING cache_key
    `;
    return rows.length > 0;
  }
```

5. Problem Solving:

**SOLVED — root cause of Telegram silent drops.** Three compounding defects in Lobu's own `LobuStateAdapter`: (1) `setIfNotExists` used `ON CONFLICT DO NOTHING` with no expiry predicate; (2) expired rows only swept inside `get()`, which this path never calls, so keys poison forever; (3) global `keyPrefix: "chat-conn"` means dedupe keys `dedupe:<platform>:<chatId>:<messageId>` are shared across all connections and orgs, while Telegram message ids restart at 1 per bot chat. Conclusive prod evidence: May-written expired rows at ids 1,2,3,4,5,6,13,15,16,17,19,21,... — every dropped message had an id in that set; every working message (hey2=8, 10, 12, synthetics 9001/9002) was in a gap. This also means **#2305's "confirmed reproducer" (KK4477 ping) was misattributed**.

**SOLVED — no provider failover exists.** Confirmed by code (`error-handler.ts:82` classifies 429 as `PROVIDER_QUOTA_EXHAUSTED` with no retry) and empirically (buremba has both z-ai and openai active and still 429s).

**UNRESOLVED — why `base_url` fixed gemini.** Setting `capabilities.text.base_url` flipped prod from `400 invalid model ID` to working (verified twice, with a reverted control). Mechanism unknown; my synthesis theory disproven. Next hypothesis: credential resolution, not module resolution. **The prod `base_url` on the gemini row is an unexplained workaround still in place** — flagged, not hidden, given the user's "no workarounds" instruction.

**UNRESOLVED — z-ai/gemini asymmetry.** `z-ai/glm-5.2` resolves to `provider=zai` with the same empty-base_url row shape.
