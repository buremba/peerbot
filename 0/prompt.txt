## Seams and surprises

1. **`SkillConfig` (DB) is a strict superset of `Skill` (declarative).** `repo`, `enabled`, `system`, `instructions`, `modelPreference`, `thinkingLevel` exist in the stored schema but have **no declarative expression**. `repo` is synthesized as `"inline/&lt;name&gt;"` / `"file/&lt;name&gt;"` (`desired-state.ts:356`) and `enabled` is hardcoded `true` (`:359`). Any "thin skills" reshape has to decide the fate of the six UI/catalog-only fields — and `agent-config.ts:454-468` already actively *strips* `modelPreference`/`thinkingLevel` on one read path, so the schema is already partly vestigial.

2. **No TypeBox/zod in the declarative layer.** The issue may assume a schema to edit; there isn't one on the CLI side — only the interfaces in `define.ts` and the loader's throw sites. The TypeBox schema is server-side only.

3. **Skill-level nix has *two* independent union points, not one.** Apply-time bake into `nixConfig` (`map-config.ts:296-305`) *and* resolve-time re-union in `platform-helpers.ts:99-125` (PR #2218). They overlap by design (the comment at `:99-107` explains: UI/catalog-enabled skills write only `skills_config` so nothing recomputes `nixConfig`). Stripping skill nix must remove both, and #2218's test file is a dedicated regression guard that will need deleting, not editing.

4. **`agent.nixPackages` and `skill.nixPackages` are entangled but separable.** Only `examples/sales/skills/account-brief/SKILL.md:4` uses skill-level frontmatter nix in-repo; `examples/personal-finance` uses agent-level. The blast radius for skill-only stripping is smaller than the raw grep count suggests.

5. **Three unrelated nix lineages share the grep.** Connector runtime nix (`worker-api/poll.ts:932`, all of `connector-worker/`, `connector-sdk/nix-package.ts`) and per-request nix (`baseOptions.nixConfig`) are *not* skill nix. Roughly half the ~60 hit files are out of scope.

6. **Behaviors do not carry skills today, and there is no join/compile step.** Skills reach the agent only via `skillsConfig` → session-context → `.skills/` filesystem sync + a progressive-disclosure prompt block. There is no place where skill content is concatenated into any prompt — `instruction-service.ts:110-140` emits only names/descriptions and tells the agent to `cat` the file. A behavior-scoped `skills` join would be the first such compile step in the codebase.

7. **Version-diffing asymmetry.** Agent settings (incl. `skillsConfig`) are a flat PATCH with no version chain; behaviors have a `watcher_versions` chain. If behavior skills compile into `prompt`, a skill edit would silently bump *every* behavior version referencing it — potentially large version churn on apply. `reaction_script` (`diff.ts:463-465, 565`) already has the opposite pathology (no drift signal, always re-pushed).

8. **Frontmatter parser is minimal.** `desired-state.ts:327` uses a single regex + `yaml.parse`, and `SkillFrontmatter` (`:317`) silently ignores unknown keys — adding frontmatter fields is cheap, but there is no unknown-key rejection today.
