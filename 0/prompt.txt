## Phase 1 — Contracts + `$skill` type definition (lobu PR 1, packages/core + server)

### 1a. Core contracts (`packages/core/src/contracts/agent-settings.ts` + new `skill-entity.ts`)

- New `SkillEntityMetadataSchema` (TypeBox) — the entity-side shape: `repo` (stable key, e.g. `bundled/x`, `system/x`, `custom/x`), `description?`, `instructions?` (the short "when to use" line), `source` (`"catalog" | "user" | "apply"`), privileged tier: `nixPackages?`, `guardrails?` (reuse `SkillPreToolGuardrailSchema`), plus `providers?`, `modelPreference?`, `thinkingLevel?`. **Not** on the entity: `enabled`, `content` (goes to `entities.content` → free FTS + embeddings), `contentFetchedAt` (metadata is fine actually — keep as optional metadata for catalog-refresh bookkeeping). Export a derived plain-JSON-Schema constant (TypeBox schemas *are* JSON Schema) used as the seeded `entity_types.metadata_schema` with `additionalProperties: false` and `x-table-column` annotations, so AJV validation and the board's auto template both come for free.
- Extend `SkillConfigSchema` **additively** with `entityId: Type.Optional(Type.Number())`. Define `SkillRefSchema = { entityId, enabled, instructions? }` and the eventual slim `SkillsConfigSchema`; during transition the stored array stays `SkillConfig[]` where an entry carrying `entityId` is treated as a reference (inline fields = migration residue/per-agent override).
- Export `PRIVILEGED_SKILL_FIELDS = ['nixPackages', 'guardrails'] as const` — the trust-tier boundary ("nothing touching provisioning"; modelPreference/thinkingLevel/providers are unprivileged).

### 1b. Type seeding + validation + trust tier (server)

Add `SKILL_ENTITY_TYPE_SLUG = '$skill'` to `packages/server/src/tools/constants.ts`.
- **Typed-shape enforcement point**: already exists — `validateEntityMetadata` at `manage_entity.ts:271/431` with the seeded `metadata_schema` (`additionalProperties: false`). No new chokepoint needed for shape.
- **Trust-tier enforcement point**: new `packages/server/src/utils/skill-entity.ts` exporting `assertSkillWriteAllowed(before: metadata|null, proposed: metadata, ctx: ToolContext)` called from `manage_entity.ts` `handleCreate` (next to line 271) and `handleUpdate` (next to line 431), keyed on `entity_type === '$skill'`. Rules: changes to `PRIVILEGED_SKILL_FIELDS` require `ctx.memberRole in ('owner','admin')` **and** a human session (`ctx.userId &amp;&amp; !ctx.agentId`), OR a server-internal trusted call (catalog install path passes `skipHooks`-style internal flag / calls `createEntity` directly with a system context). This is the right place because manage_entity is the funnel for UI, SDK, agents, and CLI apply — and because the mutation gate skips human edits (verified `entity-management.ts:654`). Belt-and-braces: a small `MutationInterceptor` (`skillPromotionInterceptor`) appended to `BUILTIN_INTERCEPTORS` in `authz/entity-mutation-gate.ts` denying `$skill` creates/updates from `principalKind === 'watcher'` — covers the promotion path (`promote-keyed-entities.ts`) that bypasses manage_entity.
- **Deletion**: soft-delete via existing `deleteEntity`; refs to a deleted entity resolve to nothing (resolver filters `deleted_at IS NULL`) — the agent-side ref becomes a dangling toggle surfaced as "skill removed" in the UI.
- **Versioning/history**: `manage_entity` already records per-field change events (`recordChangeEvent`, `manage_entity.ts:544`) — append-only audit for free. Full content snapshots (canvas-style supersede chain) deferred; see open questions.

### 1c. Resolver — the one new hot-path service

New `packages/server/src/gateway/services/skill-resolution.ts`:

```
resolveEnabledSkills(agentId, organizationId): Promise&lt;SkillConfig[]&gt;
```

Single query (PK-anchored, per GOTCHAS "read the actual SQL" — microseconds):

```sql
SELECT a.skills_config, e.id, e.name, e.content, e.metadata
FROM agents a
LEFT JOIN LATERAL jsonb_array_elements(a.skills_config-&gt;'skills') r(ref) ON true
LEFT JOIN entities e
  ON e.id = (r.ref-&gt;&gt;'entityId')::bigint
 AND e.organization_id = a.organization_id
 AND e.deleted_at IS NULL
WHERE a.id = $1 AND a.organization_id = $2
```

Materializes legacy `SkillConfig` objects: entity fields win; ref supplies `enabled` + per-agent `instructions` override; entries **without** `entityId` pass through inline (permanent fallback — required by `declared-agent-registry.ts` config-declared agents and by mid-rollout old rows). Org scoping is structural (entities are org-scoped), preserving the cross-tenant guards the current code comments insist on.

Consumer switch (all become `resolveEnabledSkills(...)` instead of `settings.skillsConfig.skills`): `platform-helpers.resolveAgentOptions`, `instruction-service.ts` `SkillsInstructionProvider`, `gateway/index.ts` worker skills sync (wire shape `{name, content}` unchanged — **no agent-worker changes needed**), `message-consumer.ts`, `auth/mcp/proxy.ts`, `output-scan.ts` (three sites), `catalog/installed.ts` `listAgentInstalled` (add `entity_id`/`entity_slug` to `detail` so the UI can link to the board), `agent-config.ts` config view, `built-in-commands.ts` count.

### 1e. Migration (one squawk-clean DML migration, modeled on `20260722010000_canvas_entity_type_backfill.sql`)

`db/migrations/2026MMDD..._skill_entities_backfill.sql`:

1. `INSERT INTO entity_types (slug,'$skill',…, metadata_schema) SELECT DISTINCT organization_id FROM agents WHERE jsonb_array_length(skills_config-&gt;'skills') &gt; 0 ON CONFLICT … DO NOTHING`.
2. Insert one entity per distinct `(org, repo, name)`: **canonical copy = the entry with the greatest `contentFetchedAt`, tiebreak newest `agents.updated_at`** (`DISTINCT ON` over a lateral unnest). `created_by` from a lateral pick on `member` ordered owner→admin→createdAt (the `resolveCanvasCreator` pattern, in SQL); orgs with no member are skipped — their agents simply stay on the inline fallback forever (resolver handles it). Slug = `lower(regexp_replace(repo||'-'||name,'[^a-zA-Z0-9]+','-','g'))`, `ON CONFLICT DO NOTHING` + re-resolve.
3. Stamp `entityId` into every matching `agents.skills_config` entry (jsonb rebuild via `jsonb_agg` join on repo+name), **keeping** all inline fields (old replicas mid-rollout keep working unmodified — this is the two-phase pattern from GOTCHAS).
4. `-- migrate:down`: `SELECT 1` (irreversible-by-design like the canvas backfill; inline blobs still present makes code rollback safe).

**Divergent-copy policy (recommended: canonical + per-agent override, not fork).** Rationale: `content` is a fetched snapshot of upstream (staleness, not intent) and privileged fields must converge to one trusted value anyway; the only genuinely per-agent authored field observed in the UI flow is `instructions` (and `enabled`). So: per-agent `instructions` differing from canonical is kept as the ref's override; divergent `content`/`nixPackages`/`guardrails` collapse to canonical. Exception: `custom/…` repos where `content` itself diverges across agents get forked into `-2`-suffixed entities (these are genuinely user-authored). Ship a pre-migration audit query in the PR body enumerating divergences per org.

## Risks

- **Hot-path resolve**: every message now touches `entities`. Mitigated: one lateral-join query replacing (not adding to) the settings read in the resolver's callers that already fetch settings; PK-anchored jsonb extraction; measure with `EXPLAIN ANALYZE` before adding any cache (GOTCHAS explicitly warns against assumed jsonb-scan claims). If needed later: short-TTL read-through cache invalidated by `updated_at` — never required shared state, so multi-replica-safe.
- **Divergent-copy reconciliation**: canonical-wins can silently change an agent's effective content where copies diverged. Mitigation: audit query in the PR body; per-agent `instructions` override preserved; `custom/` fork rule.
- **Mid-rollout replicas**: solved by additive `entityId` + retained inline fields until Phase 4 (old code reads the blob verbatim; new code prefers the entity).
- **Trust-tier regression surface**: today any member can set nixPackages; after PR 1 that becomes admin-only, a visible behavior change for non-admins using the current UI (they'll get 400s on privileged edits until PR 2/3 land). Flag in release notes.
- **Cross-org catalog type shadowing**: the type resolver's public-catalog search path (`entity-management.ts:432-458`) means a public org's `$skill` type could shadow… it cannot — tenant-local wins by `ORDER BY`, and `$` types can't be user-created. Low risk, but the seeded type should exist per-org before any instance write (`ensureSkillEntityType` at every entry point).
- **Guardrail fail-open**: guardrail call sites currently fail-open on settings errors; the resolver must preserve each site's existing failure posture (e.g. instruction provider falls back to generic blurb, mcp proxy's documented behavior) — do not introduce a new throw on entity-load failure.

## Open product questions

1. Cross-org **sharing**: is the public-visibility catalog-org mechanism (types today) intended to extend to `$skill` *entities*, or do catalog manifests remain the only cross-org channel? (Plan assumes the latter.)
2. Full **content version history** (canvas-style supersede chain / `skill_content` events) vs. the existing field-change audit events — needed for v1?
3. "Used by N agents" on the skill detail page requires a reverse jsonb containment query over `agents` — worth an endpoint in v1?
4. Should `system/` skills (repo prefix drives the "System" badge in `skill-catalog.ts`) be materialized as entities at all, or stay catalog-virtual with entities only for org-customized ones?
