## Seams and surprises (contradictions with the issue's claims)

1. **"frozen `watcher_versions.prompt` text" is only half true.** It's a *reference* (`approved_input.version_id`) re-resolved with a live SQL read at dispatch (`automation.ts:1056-1076`). It behaves as frozen only because version rows are append-only (`version-actions.ts:204`). Path C bypasses pinning entirely and reads `current_version_id` live (`activation.ts:106`) — a Behavior edited mid-conversation changes the next chat turn's instructions.

2. **The scheduled/window Behavior never gets its prompt as instructions.** `buildDispatchMessage`'s window branch (`automation.ts:1008-1052`) drops the `behaviorInstructions` it just resolved on the floor; the prompt arrives as a *tool result* from `get_content` (`behavior-mode.ts:607`). "Thin Behaviors" that assume the prompt is an instruction channel will silently not apply to the most common Behavior type.

3. **Behavior instructions are user-turn text / ephemeralContext, never system prompt.** `session-runner.ts:1770` concatenates them ahead of `userPrompt`. So the frozen prompt is *already* at the same trust level as `cat .skills` output — the override the issue worries about doesn't even require the model to disobey a system instruction.

4. **`cat .skills` is instructed even with zero skills.** `getGenericSkillsInstructions()` (`instruction-service.ts:143-146`) is the fallback for *no skills configured*, and it still points at `.skills/{skillName}/SKILL.md`. Gating on "has skills" is not sufficient.

5. **A discriminator already exists on the worker token.** `auth.tokenData.source` is signed on **both** mints (per-run `worker-token-claims.ts:103-106` and deployment-lifetime `deployment-manager.ts:668-671`, with an explicit parity comment about the #1274 P0). `gateway/index.ts` already has `auth` in hand at `:574`. But it is `undefined` for **Path C** — `message-handler-bridge.ts:1458-1476` never sets `platformMetadata.source`, only `behaviorId` (`:1242`). So a token-`source` gate would miss chat-triggered Behaviors. Fixing that is a one-line addition to `extraMetadata`.

6. **Worker-side session-context cache is a landmine for any per-session branch.** `session-context.ts:85` `CACHE_TTL_MS = 5min`, cached in a **module-level singleton keyed only on `mcpExposure`** (`:308-315`), with a stale-fallback path (`:325-330`). If you make the response session-type-dependent, the cache key must include it, or a chat turn on a reused deployment will serve the behavior-stripped context (or vice versa). Behavior runs use `forceNew: true` + `thread: watcher-${run.id}` (`automation.ts:1336-1337`) so they get fresh conversations/deployments in practice — but that's an accident of the dispatch call, not a guarantee.

7. **Skill nix has *two* independent union points, one of which is offline.** The CLI apply-time bake (`map-config.ts:296`) is not reachable from any runtime branch. Removing only the resolve-time union (#2218) yields a half-removal where CLI-managed agents keep skill packages forever.

8. **`.skills` pruning is destructive and unconditional.** `session-runner.ts:721-733` `fs.rm(recursive: true)` on any directory under `.skills` not in the current skill set. If a thin-Behavior design ships `skillsConfig: []` for behavior runs while chat runs share a workspace dir, the behavior run will **delete the chat session's synced skills**. Workspace dir is `{base}/{conversationId}` (`workspace.ts:29-37`), so this only bites if conversation ids collide — but `forceNew` behavior threads are `watcher-${runId}`, distinct.

9. **`pi` resource discovery is separately hardened.** `agent-worker/src/__tests__/pi-resource-discovery.test.ts:206, :230` guards against `.pi/skills/*/SKILL.md` in the workspace — related prior art (commit `99b50cc65`) worth reading before adding another skill-materialization branch.
