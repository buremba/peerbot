**The mutation-interceptor seam cannot do gapless numbering.** `runMutationGate` for `create` is called at `packages/server/src/tools/admin/manage_entity.ts:320` with `sql: getDb()` — a *pool* client — and the row is inserted later by a separate `sql.begin(...)` inside `createEntity` (`packages/server/src/utils/entity-management.ts:493`). So an interceptor runs in a **different transaction** from the INSERT, and its contract returns a *decision* (`allow`/`deny`/`defer`), never a mutated `entityData`. Anything allocated there commits before the insert and is burned if the insert fails — a gap by construction. `x-transitions` works at that seam because refusal needs no atomicity; numbering does.

The correct chokepoint is **inside `createEntity`'s existing `sql.begin` block**, immediately before the INSERT. (Also note: `beforeCreate` *can* mutate `data`, but it runs at line 422, before `getDb()` and outside the tx — same problem.)

## PROPOSAL — needs your confirmation (no migration written)

### DDL I would add (`db/migrations/&lt;ts&gt;_document_number_counters.sql`)

```sql
-- migrate:up
CREATE TABLE IF NOT EXISTS public.document_number_counters (
  organization_id text NOT NULL REFERENCES public.organization(id) ON DELETE CASCADE,
  entity_type_id integer NOT NULL REFERENCES public.entity_types(id) ON DELETE CASCADE,
  series text NOT NULL,                 -- '' when the type declares no series_field
  period text NOT NULL,                 -- '2026' | '2026-08' | '' for reset:never
  last_value bigint NOT NULL DEFAULT 0,
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT document_number_counters_pkey
    PRIMARY KEY (organization_id, entity_type_id, series, period),
  CONSTRAINT document_number_counters_last_value_positive CHECK (last_value &gt;= 0)
);
```

One row per (org, type, series, period) — bounded config-shaped state, no index beyond the PK, no aggregate over history. This is the exact DDL the test creates and drops, so what's proven is what's proposed.

### Locking protocol (inside `createEntity`'s existing `sql.begin`)

1. `SELECT pg_advisory_xact_lock(0x646f636e, fnv1a32(org:typeId:series:period))`
2. `INSERT … ON CONFLICT (org, type, series, period) DO UPDATE SET last_value = last_value + 1 RETURNING last_value`
3. stamp `metadata[spec.field]`
4. `INSERT INTO entities` — **same transaction**

Honest note on the lock: for the single-statement UPSERT the counter row lock alone already serializes correctly under READ COMMITTED, so the advisory lock buys no correctness *today*. I kept it because it pins the serialization point ahead of the UPSERT for any second statement the allocator later grows (manual-override check, repair path reading `entities`), and it matches the 63 existing sites. Deadlock caveat documented: two txs allocating two different series in opposite order can deadlock on the two advisory locks; PG aborts one, and the abort burns nothing.

### Rollback / gap analysis (the part that decides the design)

- **Gapless holds** only because the counter is ordinary table state mutated in the caller's tx. Rollback undoes the bump and drops the lock → the next writer reuses the number. Proven, plus a negative control proving `nextval()` does the opposite.
- **Price, stated plainly:** every concurrent create for one (org, type, series, period) serializes from allocation to COMMIT. Throughput per series = 1 / lock-hold time. This is affordable *only* because `createEntity`'s tx wraps just the INSERT (sub-ms); it would not be affordable inside a long agent-driven transaction, and no network I/O may ever sit between allocation and commit. There is no way to get gaplessness without this serialization — a non-blocking allocator is necessarily gap-prone.
- **Residual gap sources I cannot close in code:** hard-deleting a numbered document (soft delete keeps the row, which is the ERP-correct answer — you cancel, you don't delete), a manual overwrite of the field, or a resequence/backfill.
- **Residual duplicate source:** a caller passing `invoice_no` explicitly. Recommend the wiring **rejects** a caller-supplied value for a numbered field; otherwise the number is not authoritative. Your call.
- **Deferred-approval creates:** the number must be allocated at *apply* time, not at proposal time, or a rejected proposal burns a number.
- Optional second half I'd defer: a `entities.document_number` column + partial unique index as a DB-level backstop. The field name is per-type, so no generic functional index is expressible without materializing a column — bigger change, weaker payoff than the counter itself.
