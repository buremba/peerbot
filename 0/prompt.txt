Context (all verified against origin/main in this repo):
- Connectors return { events, checkpoint } only. They cannot emit entities or edges.
- `attributions` on a connector manifest eventKind resolve an event to entities and can auto-create them. See packages/connector-sdk/src/connector-types.ts:554-600 and packages/server/src/utils/entity-link-upsert.ts.
- `resolveLinksByKind` (entity-link-upsert.ts:734) already tracks matches keyed by rule AND by item index (`byRule`, `matchesByRule`), inside withEntityWriteTransaction.
- The connector sync path writes ZERO rows to `entity_relationships` today. The manifest has no `relationships` field.
- `entity_relationships` has a UNIQUE partial index on (from_entity_id,to_entity_id,relationship_type_id) WHERE deleted_at IS NULL. Columns: metadata jsonb, confidence, source, created_by, updated_by, deleted_at.
- `entity_relationship_types` has NO owner/system column; only nullable created_by (platform paths pass NULL) and a metadata jsonb.
- `member_of` is a live ACL gate (authz/channel-messages-visibility.ts:118). Lobu itself creates that type via ensureMemberOfType on any Slack/GitHub ACL sync, so it exists in an org WITHOUT anyone authoring it.
- Entity types and relationship types are owned by the org via `lobu apply`. DECIDED: connectors reference types by name, never create them.
- Today, if a referenced entity type is missing, auto-create logs a warning and returns null — silent no-op (entity-link-upsert.ts:490).
- Connectors will be written first-party, by customers using their own coding agents, and eventually some publicly exposed.
- Target use case: an ERP (invoices, customers). An invoice event names its customer; we want an invoice->customer edge.
