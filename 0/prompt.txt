### 2.4 `guardrails` — the real problem

**Readers — 5 call sites, all via `resolveAgentGuardrails`** (`/Users/burakemre/Code/lobu/packages/server/src/gateway/guardrails/aggregator.ts:88`, skill handling at `:121-132`, materialization at `:213-258`):
1. `/Users/burakemre/Code/lobu/packages/server/src/gateway/orchestration/message-consumer.ts:616` — input stage, every inbound message
2. `/Users/burakemre/Code/lobu/packages/server/src/gateway/guardrails/output-scan.ts:75` — output scan
3. `output-scan.ts:174` — withhold-stream decision
4. `output-scan.ts:217` — suggest-followups config
5. `/Users/burakemre/Code/lobu/packages/server/src/gateway/auth/mcp/proxy.ts:457` — **pre-tool gate on every `tools/call`**

**What it changes.** Two arms (`contracts/agent-settings.ts:119-127`):
- `kind: "builtin"` — resolves a registered guardrail by name (`aggregator.ts:216-227`); unknown names are logged + skipped.
- `kind: "judge"` — `aggregator.ts:233-245` calls `createJudgeGuardrail("pre-tool", entry.policy, { name, tools, model: entry.model })`. At runtime (`/Users/burakemre/Code/lobu/packages/server/src/gateway/guardrails/judge-factory.ts:111`) this makes a **real LLM call**: `judge.decide(policy, text, { model: options.model })`, with the user's `policy` string as the judge prompt and the user's `model` string as the model. `tripped: true` **blocks the tool call**.

**Answer to the privilege-escalation question: yes, concretely, and it is already true today.**

Moving `guardrails` into a user-authorable entity row would let a non-admin:

1. **Disable a pre-tool guardrail by name collision.** Dedup at `aggregator.ts:127-130` is `if (!seen["pre-tool"].has(g.name))` — first-write-wins. Agent operator entries are inserted first (`:108-119`) so they dominate *today*. But a `kind: "builtin"` skill entry naming an operator guardrail is a no-op-shaped shadow, and any reordering of that loop silently flips the precedence. The safety property rests entirely on loop order in one function, with no test asserting the ordering is load-bearing beyond the comment at `:80-81`.

2. **Neuter a judge by narrowing `tools`.** `judge-factory.ts:89-92` builds `toolFilter` from `entry.tools`, and `:98-103` returns `{ tripped: false }` for any tool not in the set. A user-authored skill with `tools: ["noop"]` produces a guardrail that never fires. And because `tools` is part of the name hash (`aggregator.ts:240`, `inlineJudgeHash(policy, tools)`), a re-narrowed copy gets a **different name**, so it does *not* collide with — and therefore does not displace — the strict one. That's the safe direction. The unsafe direction is a user simply attaching a permissive judge that runs *alongside*, adding latency and LLM spend.

3. **Pick an arbitrary judge model.** `entry.model` flows unvalidated: `aggregator.ts:246` → `judge-factory.ts:111` → `/Users/burakemre/Code/lobu/packages/server/src/gateway/proxy/egress-judge/judge-runner.ts:147,180` (`input.model ?? this.defaultModel`). **This bypasses the `models` allow-list entirely.** Compare: `agent-routes.ts:1787-1819` goes to great lengths to validate `settings.models` against the org's providers and fail-closed on a lookup error, precisely because *"the `models` list is an access gate"*. `skill.guardrails["pre-tool"][].model` is the same capability with **none** of that validation. A user could point it at an expensive model, a model the org hasn't provisioned, or a weak model that rubber-stamps.

4. **Free-form LLM prompt with cost + a bypass path.** `policy` is an unvalidated string invoked on **every tool call**. A policy of *"always allow"* on a guardrail whose name shadows a strict one is a direct bypass; a very long policy is a DoS/cost vector.

**The asymmetry that makes this urgent — this is the finding to act on.** The *agent-level* equivalent, `guardrailsInline`, is validated at write time:
- shape validation: `agent-routes.ts:1714-1723` (`validateGuardrailsInline`, rejects invalid `stage`, missing name/policy)
- judge-model requirement: `agent-routes.ts:1727-1755` — an explicit `guardrail_model_required` 400 when `EGRESS_JUDGE_MODEL` is unset

**`skillsConfig[].guardrails` gets *none* of that**, on the same route, in the same request body. So a user can express a judge guardrail through the skills field that would be **rejected** if expressed through `guardrailsInline`. The aggregator even has a defensive comment about this class of problem at `:143-146` ("*older rows or out-of-band writes*"). `guardrailsInline` is also correctly marked `"unsupported"` in the CLI (`map-config.ts:52`) — i.e. deliberately not user-authorable from config — while `skillsConfig` is `"post-load"`, i.e. fully user-authorable.

Today the exposure is bounded because the web UI has no editor for `skill.guardrails` — but nothing *prevents* it: the API accepts it, `skill-editor.tsx:46`'s `...row._original` faithfully preserves it, and any user can hand-craft the PATCH. `requireSessionOrAdminPat` (`agent-routes.ts:184-210`) allows **any web session**; admin scope is only required for PAT/OAuth callers.

**Recommendation:** `guardrails` (and `modelPreference`/`thinkingLevel`) are execution config and should **not** move to a user-authorable `$skill` entity row. Either keep them operator-owned on the agent, or gate them behind the same validation `guardrailsInline` already gets. `providers` should just be deleted.

### Migration path — **partially exists, and it is lossy**

There is a path in principle: `lobu init --from-org` already **generates** `SKILL.md` files from remote `skillsConfig` (`bootstrap.ts:396-410`), so the file layout is established and round-trippable.

But three concrete problems:

1. **No reverse migration.** Nothing reads existing `skills/*/SKILL.md` and creates `$skill` entity rows. `--from-org` goes DB→files; you'd need files→entities, and it doesn't exist.

2. **`--from-org` is already lossy** (`emitSkillFile`, `bootstrap.ts:418-429`): it emits only `name`, `description`, `nixPackages`, `content`. `guardrails`, `modelPreference`, `thinkingLevel`, `providers`, `system`, `enabled` are **all dropped**. If you use it as the migration reference, you silently drop the execution config discussed in §2.

3. **Apply is non-destructive today, which is the escape hatch.** Because `map-config.ts:291` skips the assignment when `localSkills` is empty, removing `skills:` from a user's config does **not** delete their skills — the DB keeps them and the runtime keeps serving them. So a phased deprecation is genuinely safe: ship the `$skill` entity, deprecate `defineAgent({ skills })` with a warning, and existing users' skills keep working through the web/entity path until they migrate. The failure mode is silent divergence (config says one thing, DB another), not data loss.
