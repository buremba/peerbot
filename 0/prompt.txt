## 1. The `$`-entity-type precedent

### What seeding a system entity type actually requires

There are **two** precedents and they are wildly different in size.

**`$canvas` — the minimal one.** `/Users/burakemre/Code/lobu/packages/server/src/utils/canvas-events.ts:110-122`. That's it. **13 lines**, inline inside `ensureWatcherCanvasEntity`, no dedicated file:

```
INSERT INTO entity_types (slug, name, description, icon, organization_id, created_at, updated_at)
VALUES ($canvas, 'Canvas', 'Per-Behavior canvas window', 'layout', ...)
ON CONFLICT (organization_id, slug) WHERE organization_id IS NOT NULL AND deleted_at IS NULL
DO UPDATE SET updated_at = entity_types.updated_at
RETURNING id
```

No `metadata_schema`, no `event_kinds`, no view template, no json_template, no merge logic, no cache priming. The comment at canvas-events.ts:108-111 explains *why* it exists at all: it is a fallback-avoidance hack — canvases used to bind to `$member`, "exposing canvases through the member roster and its privacy policy."

**`$member` — the maximal one.** `/Users/burakemre/Code/lobu/packages/server/src/utils/member-entity-type.ts`. The actual insert is member-entity-type.ts:242-267 and is structurally identical to the `$canvas` one (same `ON CONFLICT (organization_id, slug) WHERE organization_id IS NOT NULL AND deleted_at IS NULL`), plus `metadata_schema` and `event_kinds` JSON.

### **BLOCKER: the `$` prefix directly fights "user-visible and user-authorable"**

This is the most important thing I found. `/Users/burakemre/Code/lobu/packages/core/src/reserved.ts:12-18`:

```
/**
 * True when a type is platform-owned (hidden from rail, never pruned).
 * Sole signal: slug starts with `$`.
 */
export function isSystemEntityType(et)  { return et.slug?.startsWith("$") }
```

The header comment at reserved.ts:7 is explicit: *"Users cannot create `$…` types. Hide + prune use the `$` prefix only."* Four independent consequences, all of which you'd have to fight:

1. **Hidden from the entity-type rail AND the memory scope-bar Type dropdown.** `/Users/burakemre/Code/lobu/packages/owletto/src/components/memory/use-visible-entity-types.ts:20` filters `!isSystemEntityType(et)`. The docstring at lines 6-10 says this is "shared by the entity-type rail and the memory scope-bar Type dropdown so both show exactly the same list." So `/$owner/memory?type=%24skill` would work **only as a hand-typed / deep-linked URL** — `$skill` would never appear in the type picker or the rail. Users could not navigate to their skills.

2. **Hidden from public pages entirely.** `/Users/burakemre/Code/lobu/packages/server/src/public-pages.ts:119-120, 143, 149, 1066` — system-slug types are stripped from published type lists, from children lists, and `notFound()`ed in path resolution.

3. **Marked read-only in the UI.** `/Users/burakemre/Code/lobu/packages/owletto/src/app/$owner/entity-types/$slug.tsx:20` sets `isSystemManaged`. Also `manage_entity_schema.ts:128` stamps `is_system: slug.startsWith('$')` on every row it returns.

4. **Users literally cannot create one.** `/Users/burakemre/Code/lobu/packages/core/src/reserved.ts:120-124` → `isReservedEntityTypeSlug` returns true for any `$…`, and `/Users/burakemre/Code/lobu/packages/server/src/tools/admin/manage_entity_schema.ts:434-440` throws a 422 `"Cannot create entity type with reserved slug '$skill'"`. Only server-side `ensure*` code paths can seed a `$` type (they bypass the tool and hit SQL directly).

Empirically this matches: **`$member` is user-visible only because it has a bespoke `/$owner/members` page** (`/Users/burakemre/Code/lobu/packages/owletto/src/app/$owner/members/index.tsx`) and a `member-scope-gate.tsx` — i.e. it escapes the generic board via custom UI, exactly the thing you're trying to delete. **`$canvas` has zero UI and is intentionally invisible.** Neither is a precedent for "system-seeded AND generically browsable."

**Recommendation:** if `$skill` must be user-visible and user-authorable, do not use a `$` prefix. Use `skill` (plain slug). It is *not* in `RESERVED_ENTITY_TYPE_SLUGS` (reserved.ts:98-114) nor `OWNER_ROUTE_SEGMENTS` (26-34), so it's legal today. You lose "never pruned" protection (see §2) and gain everything else. If you want both, you'd need to split `isSystemEntityType` into two predicates (`isHiddenFromUI` vs `isPruneProtected`) — that's a change across 6 call sites in 2 packages.

## 2. Can `lobu apply` manage entity ROWS?

**No. Not remotely.** There is no row concept anywhere in the apply pipeline.

The diff kind union is closed and enumerable — grep of `kind: "…"` in `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/diff.ts` yields exactly: `agent`, `auth-profile`, `connection`, `connector-definition`, `entity-type`, `feed`, `inference-provider`, `relationship-type`, `settings`, `watcher`. No `entity`. `DesiredState.memorySchema` (desired-state.ts:285-288) has only `entityTypes` and `relationshipTypes`.

Rows are written **only** by `lobu memory seed`, and that path is *create-only, never update, never delete*: `/Users/burakemre/Code/lobu/packages/cli/src/commands/memory/_lib/seed-cmd.ts:374-390` sends `action: "create"` and swallows `"already exists"` as a no-op success (line 384-386). It never diffs, never updates an existing row, and has no delete branch at all.

### What adding rows would take

Files, in dependency order:

- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/desired-state.ts` — add `DesiredEntity` interface next to `DesiredEntityType` (desired-state.ts:46-82) and an `entities: DesiredEntity[]` to `memorySchema` (line 285).
- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/map-config.ts` (919 lines) — parse whatever new config surface declares rows.
- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/diff.ts` — a `diffEntity()` mirroring `diffEntityType` (369-430) plus a matching block in `computeDiff` (~975-1000), plus widening the `DiffRow` union.
- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/client.ts` — `listEntities()` (paginated!) + `upsertEntity()` + `deleteEntity()`, mirroring `upsertEntityType` (client.ts:632) / `deleteEntityType` (831).
- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/apply-cmd.ts` — a fetch into the remote snapshot (~line 335-412), an execution block (~800-820 is the entity-type one), and a delete-dispatch entry (line 1172: `["entity-type", (id) =&gt; ctx.client.deleteEntityType(id)]`).
- `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/render.ts:15, 28, 125` — three registry entries (label, plural, ordering).

Ballpark: **500-900 lines across 6 files.** The mechanical part is fine. The hard part is the remote snapshot: entity *types* are a bounded list you can fetch in one call; entity *rows* are unbounded. `apply` would need to paginate every row of the type on every run just to compute a diff, and identity matching (slug? id? content-hash?) is an unsolved design question, not a port.

### Prune would delete user-authored skills. Yes, really.

`computeDiff({prune})` — `/Users/burakemre/Code/lobu/packages/cli/src/commands/_lib/apply/diff.ts:907-1000`. The model for entity types (diff.ts:986-999):

&gt; anything remote-and-owned that is **not** in desired state → `verb: prune &amp;&amp; !isSystemEntityType(remoteEntity) ? "delete" : "drift"`

Note the two escape hatches that exist *today* and why:
- `ownsDefinition` (diff.ts:919-922) — never touch another org's public types.
- `isSystemEntityType` (diff.ts:995) — **`$…` types are never pruned.** That is currently the *only* thing standing between prune and destruction of platform data.

If you add rows to this loop with the same shape, then `lobu apply --prune` would **delete every skill a user wrote in the app that isn't declared in the repo config**, because from the diff's point of view a UI-authored row is indistinguishable from a row the operator deleted from config. That is a real data-loss path, not a hypothetical.

Ironically this is an argument *for* the `$` prefix (prune-protection) and simultaneously the argument *against* it (invisibility) — the same predicate controls both, which is exactly the coupling flagged in §1.

### Is there a drift-handling precedent that generalizes to rows?

Yes, and it's genuinely good — but it does **not** generalize to rows. The pattern is at diff.ts:405-428, on `eventKinds` and `viewTemplate`:

```
name: "eventKinds",
changed: (d, r) =&gt;
  d.eventKinds !== undefined
    ? !deepEqual(d.eventKinds, r.eventKinds)
    : prune &amp;&amp; r.eventKinds !== undefined,
```

The comment (diff.ts:406-411) states the intent precisely: *"event_kinds can be authored out-of-band via manage_entity_schema (a connector feed, the UI, an agent), so a config that simply doesn't declare them must NOT wipe them. Declared: diff and set on change. Omitted + prune: a present remote set is a removal. Omitted + no prune: unmanaged, never churns."* Same three-state logic for `viewTemplate` at 422-428.

This is **tri-state on a single named field of a known object**: declared / omitted-unmanaged / omitted-under-prune. It works because the *container* (the entity type) is always declared; only one of its fields is optional.

Rows are a different problem — **set membership**, not field presence. There is no "the config didn't mention this field" for a row that simply exists remotely; the row either is or isn't in the desired set. To make rows safe you'd need something the codebase does not have today: a per-row provenance marker (e.g. `metadata.managed_by: 'config'`) so prune only deletes rows apply itself created. Nothing like that exists — I checked `seedDataEntity`'s payload (seed-cmd.ts:353-372) and it stamps no provenance.

The nearest thing to a precedent is agents/watchers, which are **report-only, never delete**: diff.ts:963-971 emits `verb: "drift"` unconditionally for remote agents missing from desired state, and diffWatcher's docstring (diff.ts:461-462) says "Remote watchers without a desired model are reported as drift, never deleted." **That** — drift-report-only, no prune — is the pattern rows should copy.
