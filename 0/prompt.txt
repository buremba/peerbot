## 1. The `events` table and append-only discipline

- Provenance: `origin_id`, `origin_parent_id`, `origin_type` ("Source-native item type (post, comment, review, issue, etc.)" — :911), `connector_key`, `connection_id bigint`, `feed_key`, `feed_id`, `run_id`, `client_id`, `created_by`, `source_url`, `author_name`

- Time: `occurred_at` (when it happened) vs `created_at` (when ingested) (:862-863)

- Embedding lives OFF-table: `event_embeddings (event_id, embedding vector(768), …)` (:940-944), later stamped with `embedding_model` ("Vectors from different stamps are NOT comparable" — `20260526120000_event_embeddings_model_stamp.sql:12`) and re-keyed to `(event, model, chunk)` (`20260618140000_event_embeddings_contract.sql:1-26`).

**Append-only, quoted from the table comment** (baseline.sql:893): *"Append-only event log — the primary data substrate. … Never DELETE; supersede with a tombstone row that points at the original via supersedes_event_id."* Enforced at the DB layer by a BEFORE DELETE trigger `trg_events_append_only` / `events_block_direct_delete()` that raises unless it's an FK cascade or a transaction-scoped `SET LOCAL lobu.allow_event_delete = 'on'` (`20260610040000_events_append_only_guard.sql:28-47`).

**Updates = supersede.** The `current_event_records` view (baseline.sql:950-991) is the live-row read model: events LEFT JOINed to embeddings, filtered by `WHERE NOT EXISTS (SELECT 1 FROM events newer WHERE newer.supersedes_event_id = e.id)`. A partial unique index `idx_events_superseded_by` guarantees at most one superseder per row (concurrent-supersede loser gets a 409 — `save_content.ts:43-56, 433-448`). A denormalized inverse column `superseded_by` was added 2026-07-02 (`20260702200000_events_superseded_by.sql:36-41`): "~75% of rows are superseded" in prod, and the view is planned to flip to `WHERE superseded_by IS NULL` only after an out-of-band backfill — the column is dual-written in the same tx as the superseding INSERT (`insert-event.ts:419-429`), justified as "lineage metadata only, never payload."

## 2. Entities: table + projections, referenced by array + semantic keys

- **Entities are a materialized table, not a pure fold.** `entities` (baseline.sql:1016-1034): per-org rows with `entity_type_id`, jsonb `metadata`, own `content`, `embedding vector(768)`, `content_tsv`, soft-delete. Comment: "Type definition lives in entity_types; the row body is jsonb keyed by the type's columns" (:1040). `entity_types` (:1275-1291) carries `metadata_schema`, **`event_kinds jsonb`** (:1290), `metrics_config`, and `backing_sql`.
- **Derived (view-backed) entity types exist**: "a type is derived iff backing_sql IS NOT NULL … its data comes from running backing_sql via query_sql" (`20260529130000_entity_types_backing.sql:3-14`).
- **An event references entities two ways**: positionally via `events.entity_ids bigint[]`, and semantically via `entity_identities` — normalized `(namespace, identifier)` claims per entity, namespaces like `phone, email, wa_jid, slack_user_id, github_login, auth_user_id` (baseline.sql:1075-1109). `save_content` resolves the caller's `$member` entity through `entity_identities` (auth_user_id, falling back to email then claiming auth_user_id) and appends it to `entity_ids` (`save_content.ts:280-348`); an auto-linker scans content for entity-name mentions post-insert (:451-464).
- **A true event-sourced field fold was tried and deleted**: trigger `project_entity_field` folded `semantic_type='entity_field'` events into `entity_field_state` keep-greater-by-observation_id (`20260623040000_entity_field_grained_projection.sql`), then dropped because "NO read path ever consumed it: entity metadata is still served from the entities.metadata blob"; the already-emitted events stay in the append-only log (`20260623050000_drop_entity_field_projection.sql:3-14`). Don't claim entities are folded from events in the blog — they aren't, currently.
- **`save_content.ts`** (`packages/server/src/tools/save_content.ts`, tool name `save_memory`): `semantic_type` is required and validated against the org's `$member.event_kinds` registry plus entity-type `event_kinds` (:260-274; registry defaults `decision/observation/note/summary/guidance` in `utils/member-entity-type.ts:45-82`; validator in `utils/event-kind-validation.ts:1-10`). The **isOrgGuidance special case** (:207-236): `GUIDANCE_SEMANTIC_TYPE = 'guidance'` (`utils/org-guidance.ts:34`); guidance events are "injected into EVERY agent's system prompt," so authorship is admin/owner-gated as a prompt-injection surface, must be non-empty text/markdown, and superseding a guidance event is gated the same way as deleting it (:369-379).

## 3. Reads: visibility compilation + agent SQL via CTEs

- **`resource-visibility.ts`** (`packages/server/src/authz/resource-visibility.ts:1-113`): "THE generic resource-visibility compiler — gates connector-sourced `events` … by RESOURCE membership … at the `events` read seam." Three-state, composed AND-wise after the per-connection gate: never-graphed connection → passthrough; ACL-enforced connection → event visible only if the requester is `member_of` a `$resource` entity in `events.entity_ids`; graphed-but-stale → **fail closed** ("a stalled sync hides data, it does not leak it", :25).
- **`QUERYABLE_SCHEMA`** (`packages/server/src/utils/table-schema.ts:1-18, 307+): allowlist for `query_sql` — "A column is only safe here if it is EXCLUDED or REDACTED." Embeddings are excluded; `connections.config`/`feeds.config` are redacted in-place by a SQL expression the CTE emits.
- **CTE scoping** (`packages/server/src/utils/execute-data-sources.ts`): `validateAndScopeQuery` (:300-379) parses the SQL, allowlists tables/columns, then `buildScopedQuery` (:391+) wraps **every referenced table in an org-scoped CTE** and prepends one `WITH` block (:724). The `events` CTE reads from `public.current_event_records` (superseded rows already masked) with org scoping matching search (:540-553), then stacks per-user connection visibility + per-resource membership (:576-577). `event_classifications` are gated through their parent event via `current_event_records` "for tombstone parity" (:609-625); `channel_messages` stacks connection visibility + window + per-channel membership (:659-693). **Unknown table names are treated as entity_type slugs** — a CTE over `entities` filtered by `et.slug = $N` (:711-720), which is how derived/custom types are queryable by name.
- Headless/service callers get `principal: null` → "org-visible-only, fail-closed for private data" (:405-416).

## 4. Metric layer

- **Declared, not event-stored**: metric definitions live in `entity_types.metrics_config jsonb` — "eventSets / measures / dimensions / segments … stored verbatim as the author sent it" (`20260615120000_entity_types_metrics_config.sql:3-12`; contract types from `@lobu/connector-sdk` metrics).
- **Compiler** (`packages/server/src/metrics/compiler.ts:1-16`): "lowers a declared metric … into org-scopable SQL over the event stream"; output references `events`/`entities` as plain tables and is passed through `validateAndScopeQuery`, "which rewrites `events` → `current_event_records` (superseded rows masked)" — so metrics automatically read live state. Governing predicates = `segments` (named `where` fragments ANDed in, :81-88); v1 supports `eventSet.by:"alias"` + `reads:"current"` only.
- **Tools**: `list_metrics` is the catalog / "semantic-first discovery step: search here, then query_metric; only fall back to query_sql" (`tools/admin/list_metrics.ts:1-7`); `metric_series` is the "read-only SQL endpoint for dashboard sparklines + stat chips" with the same scoping plus 5s timeout and row cap (`tools/admin/metric_series.ts:1-25`).
- **Dashboard stats are events-sourced**: entity lifecycle changes are recorded as `semantic_type='change'` events — "Used by the metric_series SQL to compute cumulative counts (agents, connections, …) and the dashboard sparklines" (`utils/insert-event.ts:514-586`, esp. the `recordLifecycleEvent` doc at :573-586). Federated warehouse metrics deliberately stay put: "The warehouse stays source of truth; Lobu federates, never re-implements" (`docs/plans/define-metric-design.md:75, 333`).

## 5. Classification / embedding pipeline (one-paragraph version)

A raw event lands via `insertEvent` with a NULL embedding ("Embeddings are left null for background worker backfill" — `save_content.ts:7`); a `*/5` scheduled job creates per-org `embed_backfill` runs that a worker claims to vectorize the recent backlog (`scheduled/trigger-embed-backfill.ts:1-8`, with hard scan bounds after two prod incidents, :28-52). Classifiers (`event_classifiers` + versioned `event_classifier_versions` with `min_similarity`, `preferred_model`, baseline.sql:1369-1426) then label events embedding-first with LLM fallback — `event_classifications.source` CHECK is `embedding|llm|user`, rows carry `values[]`, `confidences`, `met_threshold`, `excerpts` (baseline.sql:1321-1340), with the latest per (event, classifier) exposed via `latest_event_classifications` (:1346, 1535-1548); classification normally runs inline after save, with a scheduled reconciliation as "a FALLBACK mechanism" (`scheduled/classification-reconciliation.ts:1-15`). The result is queryable three ways: FTS (`search_tsv`), vector similarity (`event_embeddings`, model-stamped), and `classification_filters` on retrieval tools (`tools/get_content/handler.ts:242-250`; `utils/content-search/types.ts:55`) — `save_memory` even reports per-row `indexing_status`/`searchable` by probing the same `needsEmbeddingSql` predicate the backfill uses (`save_content.ts:491-513`).

## 6. "Mirror of external systems" framing

There is no single code comment saying "mirror," but the framing is well-supported:
- The events table comment calls each row "a discrete **observation** from a connector or user action" (baseline.sql:893) — observations of external systems, not ownership of them.
- **Sync-in is materialization with supersede semantics**: the connector worker posts item batches; `run-lifecycle.ts:320-348` calls `insertEvent(…, { onConflictUpdate: true })` keyed on `(connection_id, origin_id)` — unchanged item → no-op, changed item → **new row superseding the old** (`insert-event.ts:246, 285-326`), serialized by an advisory lock (:27-47). `feeds` are the sync units: "Per-organization content feeds derived from a connection (e.g., Slack channel → feed, RSS source → feed)" with `checkpoint`, `last_sync_at`, `schedule` (baseline.sql:1449-1483).
- **The strongest "mirror not replace" citation** is the `channel_messages` split (`20260618130000_channel_messages.sql:3-12`): the raw chat transcript is "deliberately NOT the `events` knowledge store … Messages worth remembering are PROMOTED into `events` separately … keeping the knowledge store curated." I.e. events is a curated canonical layer, with the platform remaining the raw archive; the Slack-actions plan states it outright: "Slack is the source of truth; READ-ONLY" (`docs/plans/slack-mcp-agent-actions-and-audience.md:117`).
- For warehouses, external data is **referenced, not materialized**: derived entity types are "`backing`'d by live SQL over the warehouse's OWN semantic view" via connector query pushdown (`docs/plans/define-metric-design.md:72-75, 330-336`).
- Inversely, downstream projections of the event store are explicitly non-canonical: "Postgres/`events` stays canonical; the filesystem (and git) is a projection — a rebuildable read model, never the source of truth" (`docs/plans/knowledge-as-git.md:15`); cold tiering keeps Iceberg as "One source of truth for cold data" (`docs/plans/events-cold-tiering.md:40`).
