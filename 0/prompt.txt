## 2. Key Technical Concepts

- **Lobu monorepo**: Bun workspace, `packages/*`, `server` (gateway + runtime), `owletto` (frontend submodule), `core`, `connectors`
- **Behavior = internal `watcher`** (DB/engine vocabulary); "Behavior" is the agent-facing name, enforced by a `make pre-pr` gate
- **Two-run model**: a Behavior execution writes a `behavior` run (scheduler) AND a `chat_message` run (worker dispatch). The worker only knows the run it claimed.
- **conversationId as run identity**: `<agentId>_watcher_<behaviorId>_run_<runId>`, minted by `POST /api/v1/agents` from a server-verified `behavior_run` intent (`gateway/permissions/behavior-run-intent.ts`)
- **`agent_transcript_snapshot`**: unique index `(organization_id, agent_id, conversation_id, run_id)`, plus `agent_transcript_snapshot_latest`
- **Reaction scripts**: TS stored in `watchers.reaction_script`, compiled to `reaction_script_compiled`, run on window completion
- **`content_ids` semantics**: filters AND expands to run-mates (siblings sharing `run_id`); bypasses the default `occurred_at` upper bound
- **`analyzed_by_behavior_id`** → `EXISTS (SELECT 1 FROM watcher_window_events iwf WHERE iwf.event_id = e.id AND iwf.watcher_id = $N)` — events **read**, not written
- **Promoted entities**: `entities.metadata->>'source' = 'watcher_promotion'` AND `metadata->>'watcher_id'`
- **Prod DB access**: `kubectl exec -n summaries-prod lobu-ai-prod-db-1 -c postgres -- psql -U postgres -d owletto -A -F\t' -c "<sql>"` (DB is named `owletto`)
- **Owletto extension bridge** for browser automation: `client.operations.execute({connection_id, operation_key: "navigate"|"evaluate", ...})`; chrome connections 432 (`chrome-macbook`, NOT on this machine) and 479 (`chrome-buremba`, works)
- **Local dev**: `make dev` → DB `lobu_<branch>` on `127.0.0.1:5418`, app at `http://127.0.0.1:9359` (Vite HMR in-process; requires `Accept: text/html` or curl 404s)

The single site with the broken join. Final committed state (lines 97–121):
```
		LEFT JOIN LATERAL (
			SELECT transcript.conversation_id, transcript.created_at,
			       transcript.snapshot_jsonl
			FROM public.agent_transcript_snapshot transcript
			WHERE transcript.organization_id = ${organizationId}
			  AND transcript.agent_id = ${agentId}
			  -- NOT transcript.run_id = r.id. A Behavior execution writes two run
			  -- rows: the scheduler's behavior row (r, the one this thread is
			  -- built from) and the chat_message row the worker actually claims.
			  -- The worker knows only the run it claimed, so it posts the snapshot
			  -- against the dispatch run and run_id = r.id matched no snapshot in
			  -- production. The behavior run id reaches the worker solely inside
			  -- the conversationId, so that is the join key: POST /api/v1/agents
			  -- builds it as agentId + _watcher_<behaviorId> + _run_<runId> from a
			  -- server-VERIFIED behavior_run intent, and rejects any other caller
			  -- that tries to construct the shape (behavior-run-intent.ts). Equality
			  -- on (organization_id, agent_id, conversation_id) is the leading
			  -- prefix of agent_transcript_snapshot_latest, so this stays a seek.
			  AND transcript.conversation_id =
			      ${agentId} || '_watcher_' || ${watcherId}::text
			      || '_run_' || r.id::text
			  AND transcript.terminal_status = 'completed'
			ORDER BY transcript.created_at DESC
			LIMIT 1
		) snapshot ON true
```

## 5. Problem Solving

**Bug 1 — "random tweets" (FIXED in prod data):** behavior 71's reaction script deliberately interleaved each signal's `source_event_id` into the notification link. Source rows are `tweet`/`post` with EMPTY titles, so they render as untitled body text. Demonstrated locally: `content_ids=[16..20]` → 7 ids with **zero** raw tweets; `content_ids=[11,16,…,20]` → 12 ids **including** the 5 untitled tweets.

**Bug 2 — behavior page shows only the prompt (FIXED, PR 2587):** the transcript join used `run_id` instead of `conversation_id`. Evidence: 0 of 1434 snapshots in 30 days attached to a behavior run; 0 of every snapshot ever written. Verified at four layers — red→green integration test, corrected join against live prod (331754/334858-byte transcripts resolved), HTTP endpoint (35,690 bytes / 1 run / 4 messages), and rendered DOM in the user's real Chrome.

**Bug 3 — no created events / changed entities on the behavior page (DIAGNOSED, NOT FIXED):** three independent causes, all confirmed against prod:
- `BehaviorOutputsStrip` counts only promoted entities; behavior 71 has **0** (vs 136 observations + 22 draft_replies; 354 events total) and returns `null` with no empty state
- The `?behavior=` link maps to `analyzed_by_behavior_id` = **2,289 events read**, not the 354 written; and it only renders for agentless behaviors
- Outputs are **future-dated**: `occurred_at` stamped at window end, only 2 distinct times of day (`00:00:00`, `23:59:59.999`), **37 of 136** are `> now()`. `knowledge.read({run_ids:[878395]})` → 0; with `until:"2026-12-31"` → 5.
- Entity changes are NOT missing — `readWatcherRunThreads` attaches `actions` (approvals) and `automaticActions` (entity-merge-result); behavior 71 just doesn't change entities.
