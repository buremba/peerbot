## Seams and surprises

1. **Literal-safety is worse than "422 vs empty-render" — there is a third, silent-until-runtime mode.** `{{anything with args}}` passes `Handlebars.precompile` at save and throws `Missing helper` at render, unguarded, in both `behavior-mode.ts:475` and `get_behavior.ts:865`. A prompt that saves fine can make `get_behavior` 500 forever.

2. **Save-time and render-time use different Handlebars instances.** `renderer.ts:22` uses the **global** `Handlebars` (no `json` helper); `template-renderer.ts:79-81` uses a private `hbs` with `json`. Any future helper registered on `hbs` is invisible to validation, and vice-versa.

3. **`{{` in prose is a hard 422.** `Use {{ notation` fails `precompile`. Any skill markdown containing a lone `{{` cannot be saved at all — the issue's "literal-safety must-fix" is not hypothetical.

4. **The `version_sources`-NULL decision has a documented rationale but leaves `get_version_details` lying.** `version-actions.ts:198-203` is a deliberate choice; the collateral is `get_version_details` returning `sources: []` for all v≥2 (`version-actions.ts:456-459`). Contradicts any assumption that a version row is self-describing.

5. **`create_version` with `set_as_current: false` loses sources entirely.** The computed `sources` are only persisted inside the `if (setAsCurrent)` block (`version-actions.ts:225-266`) and `version_sources` is NULL — so the new version row records a prompt but no sources anywhere. There is also **no rollback/activate-version action** in the contract (`manage-behaviors.ts:237` action union: create/list/update/create_version/complete_window/trigger/delete/set_reaction_script/get_versions/get_version_details/get_component_reference/submit_feedback/get_feedback/list_promoted/create_from_version), so such rows are unreachable dead weight.

6. **Chip re-derivation also fires when the prompt is unchanged.** `promptEdited = args.prompt !== undefined` (`version-actions.ts:90`) — the CLI always resends `prompt` when any version-bound field changed (`apply-cmd.ts:926`), so a pure `reactions_guidance` edit on a chip-bearing Behavior silently re-derives (and can prune) sources.

7. **The default `content` source is silently destroyed by the first chip.** Created chip-less → `sources = [{content, DEFAULT_BEHAVIOR_SOURCE_QUERY}]`; a later `create_version` adding one chip → `sources = [thatChip]`. `behavior-mode.ts:378-382` re-injects the default only when the list is *empty*, so this is a real data-scope change, not a no-op.

8. **Skills do not exist on Behaviors today at all.** `SkillConfig`/`SkillsConfig` live only on the **agent** (`/Users/burakemre/Code/lobu/packages/core/src/contracts/agent-settings.ts:119-136`, persisted as `agents.skills_config`, `/Users/burakemre/Code/lobu/packages/server/src/lobu/stores/postgres-stores.ts:89`, write-validated at `/Users/burakemre/Code/lobu/packages/server/src/lobu/agent-routes.ts:1753-1812`). There is no `watchers.skills`, no `watcher_versions.skills`, and no skill field in `defineBehavior`. `/Users/burakemre/Code/lobu/packages/server/src/skills/` is unrelated (a generated MCP skill resource).

9. **Trigger kind vocabulary mismatch with the issue.** The issue's "manual" and "window" are not kinds; only `event` and `schedule` exist. A validation rule phrased over "schedule/manual/window" must be re-expressed as: schedule triggers, `execution === 'window'` event triggers, and the empty-`triggers` (manual-dispatch-only) case.

10. **`watcher_versions` has two live dead columns** (`required_source_types`, `recommended_source_types`) still projected into `query_sql` via `table-schema.ts:506-507` but never written — free real estate, or a trap for anyone reading the schema as intent.

11. `watcher_versions` has **no `organization_id`**; org scoping is derived exclusively through the `watchers` JOIN. Any new version-level table (e.g. behavior↔skill) inherits that constraint.
