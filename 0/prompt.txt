## Verdict: your public answer was wrong for this scenario. Correct it.

**10 Telegram users DMing one bot all route to the SAME agent and all run on the AGENT OWNER's connections.** There is no per-DM-sender credential isolation on a single Telegram bot. A per-user Gmail connection can be *created*, but it is structurally *unreachable* during those DM runs.

### 1. Routing: same agent, not distinct

The DM key `{platform}-{userId}` in `platformAgentId` looks like per-user routing, and that's almost certainly what misled the earlier answer — but **it is not on the message path**. It has exactly one caller, the slash-command dispatcher:
- `packages/server/src/gateway/spaces/space-resolver.ts:9-17` — the per-user ID function
- `packages/server/src/gateway/commands/command-dispatcher.ts:7,110` — its only call site (commands only)

The real inbound message path resolves agent via a different `resolveAgentId`:
- `packages/server/src/gateway/connections/message-handler-bridge.ts:580-615` — Behavior planner first, else fallback seeded with `agentId: this.connection.agentId` (line 603)
- `packages/server/src/gateway/services/platform-helpers.ts:178-243` — returns `subscription.agentId` (source `"subscription"`) or the connection's owning agent (`source: "connection"`, line ~238, logged "Routing to connection's owning agent")

Neither branch takes the sender's user id as input. One connection → one agent (or one Behavior's agent) for all 10 senders.

### 2. Principal = agent owner, NOT the DM sender — prior verification CONFIRMED

`packages/server/src/workspace/multi-tenant.ts:284-303`: the direct-auth path selects `owner_user_id FROM agents WHERE id = tokenData.agentId`, and sets `directAuthUserId` to that owner. The only override is a builder-admin turn (`tokenData.adminTools?.length`), which uses the verified per-turn admin — still never the chat sender. Header stamped at `packages/server/src/gateway/auth/mcp/proxy-shared.ts:171-173`.

`chat_user_identities` maps chat users → Lobu users, but only for approval attribution/notification targeting (`gateway/connections/interaction-bridge.ts:129-147`, `notifications/service.ts:184`). **No path makes it the credential-resolution principal.**

### 3. Answer to the scenario: NO

The trap is precise. `resolveConnectionVisibility` (`tools/admin/helpers/connection-helpers.ts:577-590`) forces any `oauth_account` personal credential to `visibility='private'` regardless of role — a DB trigger even rejects org-visible personal creds (line 614). Private connections are visible only to their creator:

`packages/server/src/authz/connection-visibility.ts:53` and `:67-78` —
```
AND (vc.visibility = 'org' OR (userParam IS NOT NULL AND vc.created_by = userParam))
```

So user #7 connects their Gmail → row is `private`, `created_by = user7`. At run time the principal is `agents.owner_user_id` (the operator). `created_by = principal` never matches. The connection exists and is invisible. Worse, the failure is *silent* — not an error, just zero rows. And whatever the operator's own `org`-visible Gmail is, **all 10 users' turns read through that one inbox.** That's the leak direction that matters.

### 4. What would actually be required

Isolation is per-agent-owner, so genuine isolation needs a **distinct agent per end user, each owned by that user** — `manage_agents.ts:359-383` supports exactly this (`owner_platform='external'` + an `agent_users` mapping, without which the agent is unreachable via chat). Your DM agent-onboarding flow is the closest existing pattern. Per-user org is the stronger variant. What does *not* work is any amount of connection configuration under one shared bot agent.
