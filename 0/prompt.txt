2. **Key Technical Concepts:**
   - **Two-tier split**: queryable (declarative policy rows, answers "may I?" pre-flight) vs enforceable (per-type code at the write seam, answers "was this attempt legal?")
   - **The split is forced, not stylistic**: three read paths gate on `action: 'read'`, and no write-seam hook can answer a read
   - **Deny-only verbs**: `deny(reason)`, `escalate(fields, reason, opts?)`. **No `allow`** — this is what makes `actor` safe in ctx (a rule can scope a denial, never loosen the lattice)
   - **Deploy-time vs write-time compilation**: code as configuration language (Terraform/CDK/Pulumi shape) — data → policy rows at apply; functions → compiled script
   - **Per-row isolate serialization is already free**: the lock at `:958` precedes the rule position at `:1101`, so two isolates cannot run against one row
   - **Write-skew**: two writes each read a stale aggregate, each passes, together violate
   - **OCC vs pessimistic locking**: Convex uses OCC + deterministic retry; Postgres SSI uses non-blocking predicate locks; Salesforce uses `FOR UPDATE`
   - **Max-restrictive fold vs most-specific ordering**: same policy rows, two different sorts (decision vs delivery target)
   - **Event-loop starvation**: per-process, not per-row — the dominant isolate risk

   Conclusions: throughput plateaus ~2,250/s from 4 workers (does not scale with cores); event loop dies between 4 and 8 concurrent isolates; bridges are cheap (~0.013ms marginal).

   **Concurrency research (primary sources):** Convex OCC — *"We know the transaction is deterministic…we can simply re-run the transaction"*; Postgres SSI — predicate locks *"do not cause any blocking and therefore can not play any part in causing a deadlock"* and *"Eliminate explicit locks, SELECT FOR UPDATE… where no longer needed"*; Odoo — SERIALIZATION_FAILURE retries, pain traced to locking the last journal entry for numbering (allocation, not validation); Salesforce — pessimistic `FOR UPDATE`, `UNABLE_TO_LOCK_ROW`.

   **Final concurrency position:** per-row isolate serialization already holds free; same-row invariants (the large majority) need nothing new; cross-row aggregates need an opt-in (SERIALIZABLE+retry or declared `locks` with `(type,id)` ordering); uniqueness → unique index; allocation → sequence, out of the write transaction.

   **Audit finding:** the trail is inverted — successful updates audited, creates/deletes/merges/links not, denials structurally invisible (rollback + post-commit placement), and `recordChangeEvent` explicitly drops rows on failure.
