## What killed it

`db/migrations/20260630000020_connections_chat_slug_unique.sql` (merged in #1623, present on `origin/main`, verified live in a migrated DB):

```sql
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS connections_chat_slug_unique
    ON public.connections (slug)
    WHERE credential_mode IS NOT NULL AND deleted_at IS NULL;
```

There are **two** unique indexes on `connections`, not one. Live `pg_indexes` dump:

```
connections_org_slug_unique  ON (organization_id, slug) WHERE (deleted_at IS NULL)
connections_chat_slug_unique ON (slug) WHERE (credential_mode IS NOT NULL AND deleted_at IS NULL)
```

`getConnection`'s query filters on `credential_mode IS NOT NULL AND deleted_at IS NULL` — which is *exactly* the partial-index predicate of `connections_chat_slug_unique`. Over that row set, slug is **globally** unique. The unscoped branch can therefore match at most one row across the whole table, so there is no arbitrary winner and no cross-tenant read. `LIMIT 1` with no `ORDER BY` is harmless because the candidate set has cardinality ≤ 1.

Critically, the migration comment shows this branch is **load-bearing by design**, not an oversight:

&gt; Orgless runtime paths depend on that: the public webhook URL `/api/v1/webhooks/:connectionId`, exclusive-transport restart, and the connection-claims lease all resolve a connection by its runtime id ALONE, with no org in hand. […] This partial unique index re-establishes the prior guarantee at the slug level.

So the org-less branch has legitimate callers, and step 4's "delete the unscoped branch outright" would have broken the public webhook route, exclusive-transport restart, and the claims lease.

## How the reproducer disproved it

The premise state is **unrepresentable**. Per AGENTS.md ("If you cannot reproduce, stop and report the dead end — do not ship a speculative fix"), I stopped. A test asserting `getConnection` returns null with no ambient org would have been green-by-construction against a state the schema forbids, while breaking three production paths.

## Where the original analysis went wrong

Fact 1 was verified against only *one* index. `connections_org_slug_unique` is real and does say per-org — but it's the weaker of two constraints. Fact 3 (no production `orgContext.run` under `gateway/connections/`) is true, and the reachability path is real: `POST /api/v1/webhooks/:connectionId` in `packages/server/src/gateway/routes/public/connections.ts:40` is unauthenticated with an attacker-controlled id. It's reachable — it just isn't ambiguous, which is the whole point of that migration. The `agents` analogy from #2284 doesn't transfer: `agents` genuinely has only `(organization_id, id)` keying with no global backstop.

## `deleteConnection` — same verdict, and note the near-miss

`softDeleteChatConnectionProjection` (`connections-projection.ts:448`) looked *worse* — its unscoped `UPDATE` has no `LIMIT`, so it reads as "soft-delete every tenant's row with this slug":

```sql
UPDATE connections SET deleted_at = now(), updated_at = now()
WHERE slug = ${slug} AND deleted_at IS NULL
```

It's protected by the same index, since only live chat rows are targeted and those are globally slug-unique. Safe, left alone. Worth flagging though: the `WHERE` clause here omits `credential_mode IS NOT NULL`, so it's protected only because live chat rows are the only ones that can collide — a data-connector row (`credential_mode` NULL, org-scoped slugs) sharing a slug *would* be caught by this unscoped UPDATE. That's a latent edge, not the reported bug, and I didn't chase it.
