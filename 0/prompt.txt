2. **Key Technical Concepts:**
- **Connection-pool deadlock**: `withEntityWriteTransaction` holds ONE pooled connection; a helper inside it calling `getDb()` needs a SECOND connection while holding the first. With `DB_POOL_MAX` concurrent writers, every slot is held and every writer waits for a slot only another writer can free. Session waits are unbounded → pool dead for the process lifetime.
- **The diagnostic signature**: exactly `DB_POOL_MAX` sessions in `pg_stat_activity` with `state='idle in transaction'`, `wait_event_type=Client/ClientRead`, all showing the SAME last query — the statement immediately BEFORE the offending call.
- `db/client.ts` already documents this exact one-directional-dependency rule for `getLockDb()` (separate small pool so lock holders camp there while work runs on the main pool).
- **`TtlCache.getOrSet` stores the resolved VALUE, not the promise** — racing misses each run the loader independently; a HIT never queries. This is why the bug only bites on cold cache (fresh test orgs, or a pod handling many orgs).
- **A local repro proves nothing without a baseline run of the same command on the unpatched tree.**
- `pkill -f "<parent>"` leaves the child alive; must kill the leaf pattern (`bunfig.gateway-lane`) and verify with `ps`.

function recordingHandle(handle: DbClient): { handle: DbClient; statements: string[] } {
  const statements: string[] = [];
  const proxy = new Proxy(handle, {
    apply(target, thisArg, args) {
      const strings = args[0] as TemplateStringsArray | undefined;
      if (strings && Array.isArray(strings.raw)) statements.push(strings.raw.join(" ? "));
      return Reflect.apply(target as never, thisArg, args);
    },
  });
  return { handle: proxy as DbClient, statements };
}
