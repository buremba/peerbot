## What I built

**Where the period lives (investigated first):** nothing in the repo has any notion of an accounting period, fiscal calendar, or close date — `grep` over `db/migrations` and `packages/server/src` for `accounting|period_close|closed_through|fiscal|lock_date` returns zero. The only per-org config surface that can hold this without DDL is `entity_types.metadata_schema` (jsonb). `organization` has only a better-auth `metadata text` column — not appropriate. So the close is declared as an `x-` vendor extension on the entity type, exactly like the `x-transitions` precedent:

```json
"x-period-close": { "field": "posting_date", "closed_through": "2026-06-30" }
```

`closed_through` is inclusive. Closing a period is an ordinary `manage_entity_schema` edit — **no new table, no DDL**.

**New:** `packages/server/src/authz/period-close-interceptor.ts` (352 lines), registered in `BUILTIN_INTERCEPTORS`. Rules: create dated ≤ close → deny; entity already dated ≤ close is sealed against *every* field including its own date → deny; open entity backdated into the closed period → deny; delete of a closed-period entity → deny; absent date = undated = allowed (and the moment it gets a closed date, the update path denies); malformed rule or unparsable date → deny (fail closed). Dates compare as UTC calendar days so a bare `2026-06-30` can't drift a day.

**Gate plumbing:** `UpdateMutationRequest` now carries `currentValues`/`proposedValues` alongside `fields` — ownership says *who* may write, the values are what let an interceptor reason about *what* the write does. Wired at every update door: `entity-management.updateEntity`, `promote-keyed-entities` (existing-row sync), and a new gate call in `entity-field-approval.applyEntityFieldChangeProposal` (an approval queued before a close must not apply after it).

**Two structural changes worth flagging:**
1. `updateEntity` previously ran the gate only for non-human edits (`if (!isHumanEdit)`). A close that binds agents but not people is not a close, so the gate now runs for every principal with `principalKind: "user"`. Approval policy is unaffected — `entity-policy.evaluateEntityFieldUpdates` short-circuits `"user"` to allow, and human writes present owner `"none"`.
2. `promote-keyed-entities` gated *creates* with one per-type probe carrying no row data, so a Behavior could promote an unlimited number of backdated new rows. Added a per-row create gate before insert (fail-closed, `deniedCreate` + a warn log); the per-type approval probe still governs approvals.

## NOT enforced (explicit)

- **`events` — completely unenforced.** Rows carry their own `occurred_at`, never touch this gate, and are written by connector sync / `save_content`. A backdated event lands in a closed period today. That is the HARD half (DB triggers on an append-only table) and I did not build it.
- **Ungated entity doors** that write metadata directly, bypassing the gate: `utils/entity-merge.ts` (entity-resolution merge), `watchers/classifier-extraction.ts`, `utils/member-entity.ts`, `utils/entity-link-upsert.ts` (attribution/identity), and `manage_entity`'s link/unlink graph edges. The `x-transitions` branch gated edges via a `$links` pseudo-attribute; I did not port that, since an edge has no posting date.
- **The close is per entity type, not per org.** Closing a month means editing every posting type's schema; nothing enforces that they agree, and there is no close history, no `closed_by`, and no reopen record.
- **Enforcement is server-side only** — direct SQL, migrations, and admin DB access are unaffected.

## Proposed DDL (needs your confirmation before building)

To make the close org-wide and auditable:
```sql
CREATE TABLE accounting_period_closes (
  organization_id text NOT NULL REFERENCES organization(id) ON DELETE CASCADE,
  ledger          text NOT NULL DEFAULT 'default',
  closed_through  date NOT NULL,
  closed_at       timestamptz NOT NULL DEFAULT now(),
  closed_by       text REFERENCES "user"(id),
  note            text,
  PRIMARY KEY (organization_id, ledger)
);
```
The type keeps `"x-period-close": { "field": "posting_date", "ledger": "default" }` (the date field is genuinely type-specific); `closed_through` moves to the table. Bounded config table, PK lookup on the read path — roughly a 10-line change in the interceptor. Reopen/close history goes to `events` as domain records, not extra columns.
